# Consult: frontend-developer (SIM-024, 2026-11-20)

## Findings
- Reusable pieces and constraints:
  - The dev-page pattern already exists in `src/app/dev/shell/page.tsx` (`NODE_ENV !== "development"` then `notFound()`). Copy it for `src/app/dev/roommap/page.tsx`.
  - `src/ui/copy/no-literals.test.ts` fails on literal JSX text and on `aria-label` / `title` literals. All renderer strings (state labels, "Seat 3", the zoom buttons) go in `src/ui/copy/roomlayout.ts`.
  - Layers (R1):
    - `src/ui/**` may import only `ui` and `lib`.
    - Manifest types, validator, hash, placement and the compositor maths go in `src/lib/sprites/` (pure).
    - Pages import `@/ui`.
    - Node-only packing code must not sit under `src/`. Put it in `scripts/` and import `src/lib/sprites` validators via a relative path or `tsx`.
- The sprite map conflicts with style guide §8 in two ways, and the ticket note settles both in the sprite map's favour:
  - Placement is by `anchor`, not bottom-alignment, and pack sprites are taller than the 16 px headroom.
  - Frames use directions s/n/w/e. Some keys are not in the §7 inventory (`wall.t.s`, `wall.inner.v`, `window.single`, ...).
  - Consequences:
    - The validator's "unknown key" set must be the union of the §7 keys and the sprite-map keys. Make it data (one `KNOWN_KEYS` list in `src/lib/sprites`) that the packer and the validator share.
    - `anchor` can be negative or positive and sprites may be taller than their tiles. Placement is `px = tileX*32 + anchor[0]`, `py = tileY*32 + anchor[1]`, with no clamping.
    - Anchor semantics: in §8 JSON, anchor is the offset from the tile's top-left to the sprite's top-left, so `drawX = tx*32 + anchor.x`. In the sprite map, anchor is the pixel inside the rect that lands on the footprint's top-left. The packer must convert: `manifest.anchor = [-mapAnchor.x, -mapAnchor.y]`. Check this against a known case, for example `desk.single.s` anchor `[2,21]`, so that the manifest value is `[-2,-21]`. Note that the §8 example's positive `[0,8]` means "sprite starts 8 px below the tile top", which is the opposite convention. Pin this with a unit test and a line in the docs.
  - Rotated footprints: `desk.single.w/e` are 1×2 in the map, while `.s/.n` are 2×1. `tiles` in the manifest is therefore per frame, and the renderer must use the footprint of the frame it selects, not the item's base size.
- Renderer: use DOM, not canvas.
  - One `<div>` per layer. Each item is an absolutely positioned element with `background-image: url(office.png)`, `background-position: -x -y`, `width` and `height` equal to the frame size, and `image-rendering: pixelated`.
  - Reasons:
    - Name tags, focus and tab order need real elements. A canvas would need a shadow DOM anyway.
    - Integer zoom: CSS `zoom` is not recommended; use `transform: scale(n)` with `transform-origin: 0 0` on a stage of fixed pixel size, wrapped in a sizing box of `w*32*n` × `h*32*n`. Integer scale plus pixelated rendering stays crisp, provided the stage's own position is integer.
    - There is no need for a canvas library, and the manifest swap works by URL alone.
  - A dense room (about 500 elements) is fine for DOM. If it ever matters, `content-visibility` or canvas can come later behind the same data model.
  - Atlas bleed: the 1 px transparent gap in §8 prevents bleed. With integer scale there is no issue.
  - Fallback when `office.json` fails to load: render an error state with copy. Do not render a blank map.
- Layering is a stable sort. Layer order comes from `manifest.layers`. Within furniture, sort by `(bottomY, x)` so items lower on screen cover higher ones (3/4 tilt rule). Chair vs desk is the usual trap:
  - A chair facing a desk from its south side (`chair.office.n`, seen from behind) should draw over the desk front.
  - A chair on the north side (`.s`) should draw under the desk.
  - Sorting by the footprint's bottom tile row plus an optional `z` bias on the item handles this. Without a `z` tie-break, items in the same row order arbitrarily.
  - Shadow layer: per the guide, a 3–4 px band at 18% `#202a3a`, generated by the renderer from the footprint (not baked). Draw it as a CSS box under the footprint's bottom edge.
  - Floors: each tile from the layout's tile grid. Walls are tile keys (`wall.*`). The renderer only looks up keys and never derives corners itself (auto-wall logic is the editor's job, 015.2); the fixture hand-lists the keys.
- Avatar compositor:
  - DOM: stack three or four absolutely positioned layers inside the 32×32 cell (body, hair, shirt).
  - Colouring needs the layer art to be greyscale (§5 uses "three greys") and tinted at runtime. Options:
    - (a) CSS `mask-image` using the atlas frame plus `background-color` per layer; masks are single-colour, so highlights and shades are lost. Or tint with `mix-blend-mode: multiply` over the greyscale frame (more complex).
    - (b) Pre-tint on a canvas once per `(layer, colour)` and cache the data-URL. Crisp, but browser-only, not testable in jsdom.
    - Recommendation: (a)/multiply if the greys have 3 tones, otherwise (b), keeping only the colour-selection part in `src/lib`. Pick one. No SVG filters.
  - Phase 1 has no final avatar art, so placeholder avatars are shapes; avatar keys always come from the placeholder.
  - The hash is pure: FNV-1a 32-bit of `sub`, then independent picks per ramp using different bit slices or salts (`sub+":skin"`). `skin = SKIN[h1 % 4]`, `hair = HAIR[h2 % 6]`, `hairStyle = h3 % 3 + 1`, `shirt = SHIRT[h4 % 7]`. Tests: deterministic, and distinct for a handful of chosen sample subs.
  - Back view when the chair is `.n` (seen from behind), front view otherwise: pure function `avatarView(chairRotation)`.
- Overlays and state:
  - State is never colour alone (§6): pending = bubble with "!", cannot = round "no" sign, mine = tint + teal outline on selection, occupied = avatar, empty = bare chair.
  - These are sprites (`state.cannot`, `state.pending`, `state.mine.tint`) placed by code, sub-tile; a pure function maps `state` to `{key, offset}`. They always come from the placeholder generator.
  - Selected/hover/focus ring is HTML (`outline`), so the seat element is the focusable `button`.
- Name tags and keyboard:
  - Each seat is a `<button type="button">` with `aria-label` from copy (e.g. "Seat 3, occupied by X"); parent is `role="group"` with a label.
  - Tag: absolutely positioned HTML, `opacity:0; pointer-events:none`, visible on `:hover` and `:focus-visible`/`:focus-within` (CSS only). Tailwind v4: `group-hover:` and `group-focus-visible:`.
  - The visible tag is `aria-hidden`; the `aria-label` carries name, status and seat number.
  - Tags must not scale with zoom: render seat buttons and tags in a second, unscaled overlay layer using zoomed pixel coordinates (`px*zoom`); only the art is in the scaled stage.
  - Keyboard order: seats sorted by row then column in DOM order. Roving tabindex later.
  - Edge clipping: `overflow:auto` on the room wrapper; flip the tag below when `tileY < 2` (pure, testable).
  - Touch: tap = focus shows the tag. At 390 px the room at 3× scrolls horizontally; never use a non-integer zoom. Offer "auto" (largest integer that fits) besides 1/2/3.
- Atlas plumbing:
  - Manifest loader: runtime `fetch("/sprites/office.json")` with `cache: "no-cache"` or a `?v=` version query, so a replaced PNG is not served stale (AC 3).
  - Validator (`src/lib/sprites/manifest.ts`): rejects unknown keys; rejects out-of-bounds frames (needs `"size": [w,h]` in the JSON, written by the packer); checks directional sets (pick a rule and test it); checks `tile` is 32 and `w`, `h` positive integers; returns typed errors (`{path, message}[]`), not exceptions.
  - Packing script and CI: the committed `public/sprites/office.png/json` is generated locally; CI must not repack and compare. If the committed atlas holds Imersa sprites it redistributes the pack, which the licence forbids in a public repo, so the committed atlas should be placeholder-only and the pack-based atlas built locally and git-ignored or written elsewhere. Needs Ming (open question 1).
  - Missing sheet: warn per key, use the placeholder, exit 0. Missing `export/` is not an error; a missing map key only warns. Wrong export canvas size or unknown key: exit 1.
  - PNG I/O: `pngjs` (pure JS) or `sharp` would be a new devDependency (stack rule: flag it). `pngjs` avoids native builds.
  - Packing: simple shelf packer, 1 px gap, deterministic order (sorted by key), byte-stable output.
  - Placeholders: rect lists per key in the §3 palette, 1 px outline, no shadow; footprint and anchor in the same convention as the sprite map so swapping sources moves nothing.
- Dev demo page: `/dev/roommap`, dev-only via `notFound()`, zoom buttons, fixture in `src/ui/roomlayout/fixtures.ts` (or `src/lib` so tests reuse it) showing every seat state and at least 3 distinct subs. Check whether `no-literals` scans `src/app/dev`, and that dev pages do not break `check:layers`.
- Testability with Vitest:
  - Pure tests in `src/lib/sprites/*.test.ts`: validator (valid placeholder manifest; unknown key; out-of-bounds; missing direction; plus one test loading the real `public/sprites/office.json`); hash; placement (tile → px with anchor, zoom, layer order, rotation → frame key and footprint, tag flip); packer logic as pure functions over in-memory RGBA buffers with a thin I/O wrapper.
  - Component test (check jsdom vs happy-dom): seats are buttons with the right labels, tags in DOM, stage has `image-rendering: pixelated` and integer width. Hover is CSS-only, verified visually.
  - Test `layersFor(sub, view)`, not visuals. Confirm `check:layers` ignores `scripts/`.

## Recommendations
1. DOM renderer with a scaled art stage and an unscaled overlay layer for seat buttons and name tags (AC 2, 5; D50).
2. Everything computable in `src/lib/sprites` (types, `KNOWN_KEYS`, validator, anchor conversion, placement, hash, seat-state → overlay, tag flip). Tests cover AC 6.
3. Add `"size": [w,h]` and optional `"version"` to the manifest (backwards-compatible extension of §8), update the style guide in the same PR, cache-bust the loader with `version`.
4. Make the packer's anchor conversion explicit and tested (sprite-map anchor is the negated manifest offset); document it.
5. Per-frame `tiles`; footprint comes from the selected rotation's frame.
6. Overlays and avatars always from the placeholder generator.
7. Copy file `src/ui/copy/roomlayout.ts`, `satisfies Record<SeatState,string>` for state labels.
8. "Auto" integer zoom plus 1/2/3 for 390 px.

## Risks
- Licence: committing a pack-derived `office.png` into a public repo contradicts the sprite-map note. Highest risk (open question 1).
- Anchor convention mismatch would shift every pack sprite; a test with 2 known anchors prevents it.
- Chair/desk sort artefacts because pack sprites overhang (about 58 px tall for a 1-tile chair); an optional per-item `z` bias may be needed (name it now for SIM-015.1).
- Greyscale avatar tinting depends on art that does not exist yet; placeholder avatars should be greyscale too to prove the pipeline.
- Stale browser cache after swapping `office.png`.
- Fractional DPR (125%, 150%) can seam a scaled stage; verify manually; consider per-zone repeating floor backgrounds.
- `pngjs`/`sharp` is a dependency change (stack rule).
- Hover-only tags on touch: mitigated by focus on tap and `aria-label`.
