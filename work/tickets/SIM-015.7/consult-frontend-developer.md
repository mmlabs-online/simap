## Findings
- Core (`src/lib/layout-editor`) is ready: `draftFromLayout`, `placeItem/placeFromTray/moveItems/rotateItems/deleteItems/resizeRoom` (return `OpResult` with a rule `code`), `history` (`startHistory/commit/undo/canUndo`, 50 steps), `tiles` (`pointToTile`, `dragDelta`, `itemAt`, `itemsInRect`, `footprintCells`), `save-plan` (`isDirty`, `planSave`, `assignCreatedSeats`, `buildSavePayload`, `forgetDeletedSeat`, `restoreRemovedSeat`), `paletteEntries`. Everything needed is pure and unit-tested; the UI is wiring only.
- `RoomMap` paints via `buildDrawList(layout, seatViews, manifest)` and `paintRoom`; it owns atlas loading, zoom clamping and a scroll region. `list.bounds` is the pixel origin used by `pointToTile`. It takes a `RoomLayout`, so the editor can feed `draftToRoomLayout(draft)` plus a `seatViews` map. Gap: it has no pointer layer and no selection highlight, and the atlas loading is internal. Also `bounds` may not start at 0,0 if the draw list pads. Verify before using `pointToTile`.
- `MapView` has no `version` (`map-view.ts:4`, `toMapView` ignores `body.version`; server returns `version` at `layout.ts:120`). The PUT response is the same `LayoutResponse`, so after a save it can go through `toMapView` and yield the new baseline and version. `seatsApi` has no `saveLayout`; it needs `call` with PUT and JSON, and should reuse `toMapView` for the result.
- Room id comes from `roomCode` via `useRoomSeats` resolution (`SeatsPage.tsx:50-57`), which also does 404 handling. The edit page is a server stub; `params` is a `Promise<{roomCode}>` (see `rooms/[roomCode]/page.tsx`). Tier comes from `useSession()?.tier` and `canManageSeats`.
- `useRoomLayout` is reusable for the initial load. It keeps the old view on transient errors, which is wrong for the editor after a conflict: the editor needs an explicit Reload that rebuilds the draft and baseline.
- Server PUT is admin-tier, `{tier:"admin"}`. The 409 codes `layout_stale` and `layout_seats_changed` come through `errorCode`, and the copy is in `copy/api.ts:30-31`.

## Recommendations
1. Structure (all in `src/ui/roomlayout/`, `"use client"`):
   - `LayoutEditorPage` (data, access, route state): resolves room via `useRoomSeats`, loads via `useRoomLayout`, gates on tier (not allowed state), `truncated` (read-only message), mobile notice. Mounts `LayoutEditor` with `key={version}` so Reload resets state.
   - `LayoutEditor` (state): one `useReducer` holding `{history, baseline, baseVersion, selection: Set<string>, tool: sprite|null, zoom, saving, error}`. Pure `editorReducer(state, action)` in `src/lib/layout-editor/` or `src/ui/roomlayout/editor-state.ts` exercises the core ops, maps a refused op to an error code, commits on success. Keep it a pure function so most behavior is tested without DOM.
   - `EditorCanvas`: wraps the painter plus a transparent pointer overlay div sized like the canvas. Best to extract the atlas and canvas part of `RoomMap` into a hook or sub-component (`useAtlasPaint`) instead of duplicating it. Add a selection/ghost layer as absolutely positioned divs (cheaper than repainting).
   - `Palette` (fixture list plus tray seats), `Inspector` (selection, rotate/delete, room w×h), `EditorToolbar` (Undo, Zoom, Save, Cancel/Back), `ConflictBanner` with Reload.
   - Copy in `copy/roomlayout.ts`. Edit link in `RoomMapSection` gated by `canManageSeats(tier)`, and hidden when `truncated`. Pass a prop `editHref`, not a tier, so the component stays easy to test.
2. Pointer: use Pointer Events with `setPointerCapture` on the overlay; convert client coords with `getBoundingClientRect` on the overlay (scroll-safe as it sits inside the scroll content). State machine: idle, tool-place (click on tile calls `placeItem` or `placeFromTray`), drag-move (pointerdown on a selected/hit item, then `dragDelta` from the start point, show ghost preview via `moveItems` result without committing, commit once on pointerup = one undo step), marquee (pointerdown on empty, `itemsInRect`). Shift adds to selection. Pointercancel aborts without committing. Set `touch-action: none` only while a tool or drag is active, otherwise scrolling pan breaks.
3. Keyboard: make the overlay region focusable (`tabIndex=0`, `role="application"`-ish with a label, or keep `region`), handle R, Delete/Backspace, Ctrl/Cmd+Z, arrows (move 1 tile), Esc. Ignore keys when focus is in an input (room size fields). Provide button equivalents in Inspector for all of them (WCAG 2.1.1, no keyboard-only path to select an item otherwise: add Tab-cycling or a list of items in the Inspector, or arrow-based cursor tile + Enter to place/select). Announce op results and refusals in an `aria-live` region.
4. Save: `planSave`, then DELETE each removed seat (`seatsApi.remove`), then POST `add(roomId, n)` for new desks (in slice 2 there are none, since desks are SIM-015.8, so `createKeys` is empty; still handle the flow or assert). Then `buildSavePayload(draft, baseVersion)`, a client-side count-limit check against `LAYOUT_LIMITS` (fixtures, seats, floor cells) before the PUT, then PUT. On success: `toMapView(response)` becomes the new baseline, draft, and version; clear selection (keys change). On a mid-sequence failure use `forgetDeletedSeat` / `restoreRemovedSeat`. Also enforce the limits at place time (refuse with a message) so the user finds out early.
5. Leave guard (Next 16, no route blocker):
   - `useLeaveGuard(dirty, confirm)` hook: `beforeunload` listener (add only while dirty; `preventDefault` and set `returnValue`); capture-phase `document` click listener that finds the nearest same-origin `<a href>` (skip modified clicks, target=_blank, same-URL hash), calls `preventDefault` + `stopPropagation` then `window.confirm` or a dialog; on confirm, `router.push(href)` after the guard disarms. Capture phase on `document` beats Next's `Link` onClick handlers. Own Back/Cancel call the same `confirmLeave()`.
   - Make the confirm injectable (`confirm` prop or `useConfirm`) so tests do not depend on `window.confirm`. Prefer the app's dialog if one exists.
   - Disarm the guard after a successful save and when `dirty` is false (`isDirty(baseline, present)`).
   - The browser Back limitation stays documented (A9); add it to the PR text.
6. Errors: a pure `mapLayoutError(code)` (409 `layout_stale`/`layout_seats_changed` gives `{kind:"conflict"}` with Reload; `forbidden`/`unauthenticated` give access states; 422 rule codes give a rule message; else `apiErrorMessage`). Reload action: `reload()` then rebuild draft with a new key; warn that local edits are discarded.
7. Tests (Vitest + testing-library, check how existing `RoomMap.test.tsx` mocks canvas/atlas):
   - Pure: `editorReducer`, `mapLayoutError`, `toMapView` version, `saveLayout` request shape and result, pointer-math helper (client rect to tile, drag state machine as pure function `pointerReducer`).
   - Component (the AC): leave guard (dirty: beforeunload `defaultPrevented`, link click blocked until confirmed, Cancel confirms; clean: no interference; after save: disarmed), error mapping (409 shows Reload), non-admin shows not allowed, truncated read-only. Stub the canvas painter (mock `./paint` and `loadAtlas`) and test pointer via `fireEvent.pointerDown` etc. with mocked `getBoundingClientRect`.

## Risks
- Duplicating `RoomMap` atlas/paint code. Extract first, and keep `RoomMap.test.tsx` green.
- jsdom lacks `setPointerCapture` and `PointerEvent` details; guard calls (`?.`) and polyfill in tests.
- Capture-phase link guard also fires on in-editor links (palette buttons are not links; verify) and on `router.push` calls, which it does not see (programmatic navigation bypasses it; fine for Back/Cancel only if they use the guard).
- Partial save: DELETEs succeed, then the PUT 409s. The baseline must be updated for what was deleted, or the user retries a state the server already changed (core helpers exist; the reducer must use them).
- Large rooms (64x64, 500 seats): re-running `buildDrawList` per pointermove during drag. Throttle with rAF and only recompute the preview on tile change.
- Next 16: `useSearchParams`/`useParams` in client components need a Suspense boundary if used in the page; the page itself stays server and passes `roomCode`.
- Stale `seatViews` for the painter: the editor has no occupancy, so pass states as `empty` (or the map's existing views) and make sure selection is not painted as seat state.

## Open questions
- Should the guard use `window.confirm` or an app dialog (is there a `ConfirmDialog` in `src/ui`)? Needs one for consistent copy and tests.
- Keyboard-only placement and selection: acceptable to ship arrow-cursor mode, or is an Inspector item list enough for A11?
- Does a successful PUT with unplaced seats left over (tray non-empty) stay blocked (A5)? Confirm the Save button's disabled reason is shown.
- Zoom state: share with the room page, or independent (default 2)?
