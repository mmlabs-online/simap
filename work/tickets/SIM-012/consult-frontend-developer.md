## Findings

**Existing UI patterns (reuse)**
- The room detail page is a stub. `src/app/(app)/rooms/[roomCode]/page.tsx:4-12` renders `PageSkeleton`. The route param is `roomCode`, and `src/lib/nav.ts:37,55` already points the `/rooms/[roomCode]/edit` link at it. `RoomCard.tsx:7` says "Links nowhere (D47)", so a link from card to detail is new work.
- Page pattern is `RoomsPage` (container: `useApiFetch`, `createRoomsApi`, `useRooms`, dialog state) over `RoomsView` (pure view with `status` loading/error/ready, skeleton, error card with retry, empty card). See `src/ui/rooms/RoomsPage.tsx:20-60` and `RoomsView.tsx:23-107`. Mirror it for `SeatsPage` / `SeatsView`.
- The API client is `createRoomsApi(apiFetch)` (`rooms-api.ts:19-72`). Each method resolves to `{ok,value}|{ok:false,code}` and never throws. `useRooms.ts:10-37` drops stale responses with a counter ref and a mounted ref. Copy this for `useSeats(roomKey)`.
- Dialogs use `EntityFormDialog` (native `<dialog>`, Esc, focus return, an `error` line with `role="alert"`; `src/ui/EntityFormDialog.tsx:14-115`), plus `DialogField` and `DialogSelect`. `DeleteRoomDialog.tsx:27-95` is the model for delete and replace-confirm. Its `not_found` and refetch-on-conflict handling at lines 45 and 62-63 is the pattern for stale data.
- Copy goes in `src/ui/copy/<feature>.ts` (D36). `no-literals.test.ts:9-10,42-49` scans every `.tsx` under `src/ui` and `src/app` for JSX text and for `title`, `label`, `aria-label` and similar props. The copy files must have no diacritics (`:52-60`). `apiCopy.errors` is `satisfies Record<ApiErrorCode,string>` (`src/ui/copy/api.ts:4-21`), so every new server code needs an entry in `src/lib/api/error.ts:1-16` and in `apiCopy.errors`.
- `apiFetch` re-sends once on 401 or 403 (`src/lib/api/fetch.ts:57-75`). It also throws `ApiAccessError` instead of returning a 403 `Response`, so the API client maps it to a code. This is R7: domain refusals must be 409 or 422, never 403. That includes "not your seat" on release, "cannot-seat" and "seat not empty", or the write could repeat.

**Seat API shape and route conflict**
- Existing room API routes use `[id]` (a canonical UUID, `src/app/api/rooms/[id]/route.ts:13-16`, plus `delete-impact`). The ticket's `POST /api/rooms/{code}/seats` and `DELETE /api/seats/{code}` use codes. Next.js rejects different slug names at the same path level, so `src/app/api/rooms/[code]/seats` would collide with `rooms/[id]`. Either the segment stays `[id]` (room UUID, with the UI resolving code to `RoomDto.id` from the rooms list), or the plan decides explicitly. Seat codes like `C302-04` are unique per org (`db/migrations/20261120150000_init.sql:100`). Room codes are renamable (`renameSeatCodes`), so seat codes change on a room rename. This matters for `?seat=<code>` links and stale panels.
- Schema already has `seats.cannot_seat` and `cannot_seat_reason`, `occupant_id`, `group_id`, `project_id`, and `devices.role` with the partial unique index `devices_one_primary_per_seat` (`init.sql:93-94,137`). No migration should be needed (R2). The invariant-3 trigger is deferred to commit (`init.sql:223`), so replace and demote must happen in one transaction.
- `RoomDto` (`src/lib/rooms/types.ts:1-9`) has no seat data and no tier or role field. A new `SeatDto` is needed: id, code, roomId, cannotSeat, reason, occupant `{id,displayName}`, devices `[{id,name,role,ownerName}]`, group, project. Use server-computed `status` (SEA-02). Add a room-by-code read, e.g. `GET /api/rooms/[id]/seats` returning the room header and seats. A room fetched by code is not available from the list alone without filtering client-side.
- Picker source already exists: `GET /api/members` is tier user, accepts `q`, `status` (`active`) and a cursor, with max limit 100 (`src/app/api/members/route.ts:9-19`, `MEMBER_LIMITS`). Reuse it with `status=active` and debounced `q`. No new endpoint is needed. Members who are only known via Identity are excluded already (D16). Check that `parseMemberQuery` supports `status=active`.
- Role gating: `session.tier` plus `atLeastTier` (`RoomsPage.tsx:23-24`). Admin sees add and delete seats. Manager+ sees assign, remove and cannot-seat. The occupant sees release. Compare the session's member id to `occupant.id`; check what `useSession` exposes (it may lack a member id and need `/api/me`).

**D47 / D52 reading**
- D47: seat management is in the clean UI kit, with the seat panel "opened from the list (`?seat=<code>`)" and no map. D52: the pixel/game style applies to end-user surfaces, including "the seat panel opened from the map", while "room/seat tables" are management screens in the clean kit and body text, tables and forms never use a pixel font. So there is no hard conflict:
  - the seat table is clean, per D52;
  - the panel opened from the map is pixel, but this panel is opened from the list;
  - the ticket says UI style A, no pixel art, and the sprites and map are BLOCKED.
- The soft conflict is that the SEA-05 panel is the same component D52 later wants restyled pixel-style once the map ships. Build `SeatDetailPanel` as a presentation component with data and handlers as props, with no map assumptions, so a pixel skin can wrap it in SIM-015.x. Record in the plan that the panel is clean-kit now (ticket plus D47 win) and the restyle is a follow-up.

## Recommendations

1. **Route and page.** Keep `[roomCode]` for the page. Fetch the room via the list (`useRooms`) or a new `GET` by code. Pick one and key the data by room id. Room switcher: a `<select>` or `DialogSelect`-style control built from `useRooms`, navigating with `router.push(/rooms/${code})`. Re-key by rendering `<SeatsPage key={roomCode} />` (or `key` on the container) so panel, dialog and fetch state reset when the room changes (AC "route re-key").
2. **`?seat=<code>` panel** (AC 3). The page reads `useSearchParams`. This is the first use of it in `src/ui`. A page using it must be wrapped in `<Suspense>` for the static build, or be a client component below `AuthGate` (check). Open a row with `router.push("?seat=C302-04")` (back button closes the panel, which matches SEA-05 "addressable by URL") and close it with `router.replace`/`back` to the same path without the param. On refresh, fetch the seat by code: if the seat is not in this room, or the code is unknown, show a `not_found` state in the panel and offer a close action. Never trust the param. Encode with `encodeURIComponent` and cap the length. Validate against the seat-code shape.
3. **Panel as a modal dialog on small screens, side drawer on wide ones.** Reuse the native `<dialog>` approach for focus trap, Esc and focus return. At 390 px it should be a full-width sheet (`w-[calc(100%-2.5rem)]` as in `EntityFormDialog.tsx:71`). Return focus to the row that opened it.
4. **Seats table.** Use a real `<table>` with `<th scope>`. The row action is a native `<button>` in the code cell, not `onClick` on `<tr>` (keyboard and screen reader safe). At 390 px, hide the devices column or stack it, or make the table `overflow-x-auto` with the code and status columns sticky. Status is text plus icon, not colour alone (cannot-seat shows the reason). Names keep diacritics; use `localeCompare("vi")` or server sort and `truncate` with a `title`/`aria-label`.
5. **Mutation flow (single source of truth).** After every mutation, and on any 409/422/404, call `reload()` for the room's seats and also for the open seat. Keep the panel's data derived from the list plus a seat-by-code fetch, not a separate cache. Server returns the fresh `SeatDto` on success. Replace flow: assign returns 409 with a code like `seat_occupied` and the current occupant `{id,name}`, and the UI shows "X sits here. Replace with Y?" using the server's occupant name, not stale client data. Confirm resends with `replace:true` and the expected occupant id, so a concurrent change gets 409 again. Make release, assign and remove idempotent (assigning the same occupant is a no-op, SEA-03).
6. **Disabled states.** `cannot_seat` disables Assign in the UI and the server refuses with 409/422 (AC 5). Add-seats `count` has a client cap matching the server (e.g. 1 to 50), and the form shows a field error. Delete uses a confirm dialog, with `seat_not_empty` mapped to a clear message (AC 2).
7. **Picker.** An accessible combobox or a searchable list in the dialog: `q` input with debounce (stale responses dropped via a counter, as in `useRooms`), the first 50 active members, "load more" with the cursor, and an empty and error state. Exclude nothing client-side. Show `displayName` and the employee code to tell apart same names. Use a listbox with `aria-activedescendant` or a simple radio list. A radio list is the lower-risk option in a native dialog.
8. **Testability.** Put pure logic in `src/lib` or `src/ui/seats/*.ts`: role gating (`canAssign`, `canRelease(session, seat)`), the replace-confirm text builder, the `?seat` parse and format, the row view-model, and the add `count` validator in `src/lib/validate/seat.ts`. Components are pure views with props, tested like `RoomsView.test.tsx`. API client tests mirror `rooms-api.test.ts`. Server rules (assign, replace, release, demotion, group inherit, delete guard, counter) as unit tests with a fake client in `src/server/seats/*.test.ts` plus `*.db.test.ts` for the transaction and the deferred trigger. Add a `routes-guarded.test.ts` entry for the new routes.
9. **Split proposal (size L).** SIM-012a (API and server rules, tests): add and delete seats, assign, replace, release, cannot-seat, group inheritance, seat read endpoints, audit rows. SIM-012b (UI): room detail page and seats table, room switcher and re-key, add and delete UI, seat panel with `?seat`, assign, replace, release and cannot-seat dialogs, picker. If it must stay one ticket, build in this order: server and API, read-only page and table, panel and URL, then mutations.
10. **Add** `seats` to the `ApiErrorCode` list and `apiCopy` (e.g. `seat_not_empty`, `seat_occupied`, `seat_cannot_seat`, `not_occupant`), and a `seatsCopy` file. Add `RoomCard` link to `/rooms/{code}`. No new nav rail item.

## Risks

- **API slug conflict** `rooms/[code]/seats` vs the existing `rooms/[id]` (build error). Also `DELETE /api/seats/{code}` carries a code that changes on room rename, so mutations should key on seat id with the code only used for display and the URL.
- **R7**: any "not your seat" or "cannot seat" refusal using 403 gets re-sent by `apiFetch` and could repeat a write. Use 409/422.
- **Concurrent edits**: replace and release can race (two managers). Use the room `for share` and seat `for update` lock order in `src/server/README.md:11`. Add and delete seats use the room `for update`.
- **`useSearchParams`** can break the build without Suspense. `?seat` for a seat in a different room could leak data if not scoped by `org_id` and room (R6).
- **Large rooms**: a plain table of all seats is fine for now, but with hundreds of seats the response and table can be slow. Add a sensible cap or pagination note.
- Panel style in D52 will need a restyle later. Duplicated work is avoided if the panel is props-driven.
- Dialogs: `EntityFormDialog` has a fixed `max-w-[440px]` and the picker list needs scroll inside it. Check the 390 px height with the keyboard open.
