## Findings
- Editor today: `EditorCanvas.tsx` has a click layer (`aria-hidden`, onClick/onMouseMove only). It already has a ghost div (`place-ghost`: primary when ok, dashed error when refused) and selection outlines. Pure helpers `dragDelta`, `pointToTile`, `itemsInRect` and `itemAt` exist in `src/lib/layout-editor/tiles.ts` but are unused by the UI. `canvasTile` (canvas-point.ts) maps client px to a tile, or null outside the room.
- Reducer (`editor-state.ts`): `move {dx,dy}` goes through `moveItems` and `checked()`. A refusal sets `notice {kind:"refused", code}` with no history change, so snap-back is free: the drag never mutates the draft. Refusal copy exists (`out_of_bounds`, `overlap`) and `EditorStatusLine` is `role="status"`.
- `select` only supports one key or a shift-toggle. There is no action for "set selection to this key list" (marquee needs one).
- History: `commit` is one step per op, limit 50. Inspector arrows = one step per click (SIM-015.7 plan A12 said "no coalescing there"; coalescing was explicitly left to .10).
- Keys: the only handler is the wrapper `onKeyDown` in `LayoutEditor.tsx` (Esc via `escDisarms`, which already checks dialogOpen/defaultPrevented). Undo/Save exist only as toolbar buttons. Seats are not deletable (`delete` action returns `seat_delete`). Tray seats cannot be moved by the pointer.
- Placement tool is armed: click places. Drag and marquee must be inactive while a tool is armed (the pointerdown path must not start a drag).

## Recommendations
1. Pure state machine in `src/lib/layout-editor/pointer.ts` (lib, so it is unit-testable). States: `idle -> pending(down tile, hitKey, shift) -> dragging(items, dx,dy) | marquee(a,b)`. Use a threshold of at least 4 px or a tile change before leaving `pending`, so a plain click still goes through `onPick`. Pointerdown on an unselected item selects it first (shift = additive), then drags the selection. Pointerdown on a selected item drags the whole selection. Pointerdown on empty space starts a marquee, and a click on empty space with no movement means selectNone (current behaviour). Shift+marquee adds to the selection. Add a reducer action `selectMany {keys, additive}` (reuse `itemsInRect`; filter to existing keys).
2. Drag feedback: draw a ghost for each selected item at the offset position, reusing the `place-ghost` styling. Ok = primary. Refused = dashed error. Compute the verdict by calling `moveItems(draft, sel, dx, dy)` in a `useMemo`, so the ghost and the commit use the same rule (no second rule). Keep the originals visible (dimmed) while dragging. Drop: dispatch one `move {dx,dy}` on pointerup. A refused result sets the existing refused notice, and the ghost disappears, so the snap-back is the draft staying unchanged. Add a drop-specific message only if the refused text needs context, e.g. `dragRefused: (reason) => "Not moved. " + reason`. The existing refusal strings are fine, so I suggest reusing them to stay minimal. Pointercancel and Esc during drag cancel with no notice. Esc while dragging must cancel the drag first, then the tool (the tool is not armed during a drag anyway).
3. Marquee feedback: an absolutely positioned dashed rect in the click layer (tile-snapped or pixel; pixel is smoother, and the tiles are computed on pointerup/rAF). Live-highlight the would-be selection using the same `itemsInRect` call so the user sees the result before release. Use `setPointerCapture` on the click layer. Set `touch-action: none` only while a drag or marquee is active (the editor is desktop-only; the style can be set in pointerdown and cleared at the end). Throttle pointermove with rAF and keep the pending point in a ref.
4. Shortcuts (pure `keyAction(e, ctx) -> EditorAction | "save" | null` in lib, tested as a table):
   - R: rotate. Delete/Backspace: delete (`seat_delete` notice if a seat is selected; do not hide the key, because the notice explains why). Backspace is also "browser back" in no browsers now, but still preventDefault only when handled.
   - Ctrl/Cmd+Z: undo (no redo exists; do not claim Shift+Z). Ctrl/Cmd+S: preventDefault always (stops the browser save dialog), then run `save()` only if `canSave`, otherwise show the existing saveBlock reason via the status line.
   - Arrows: move the selection by 1 tile. Shift+Arrow is optional (a 5-tile jump); skip unless cheap.
   - Esc priority: (a) dialog open (do nothing), (b) cancel a drag or marquee, (c) disarm the tool, (d) clear the selection. Only (c) exists now, so keep `escDisarms` and add the others after it.
   - Ignore when the event target is input, textarea, select or contenteditable, when a modal or dialog is open (`guard.pending`), when `e.defaultPrevented`, when `isComposing`, and for Alt combos. The R, Delete and Arrow keys must not fire when focus is on a button (Inspector buttons, toolbar) for arrows only if that would conflict; arrows on the focused region are the intended case. Arrow keys on a focused Items-list button should not hijack. So scope: handle R/arrows/Delete only when the focus is on the canvas region (tabIndex 0) or on the body of the editor, not on buttons or sliders. Ctrl+Z/Ctrl+S can be editor-wide, except in inputs (native undo in text fields must keep working).
   - Respect `frozen` (read-only or saving): the reducer already blocks, but Ctrl+S must also be a no-op while saving.
5. Arrow coalescing: commit-on-first and merge-on-repeat, so each press shows immediately and undo returns to the state before the burst. Implement it in the reducer: `move` gets an optional `coalesce: true`; keep `lastMove: {keys, at}` in state (or a `coalesceId`), and if the previous committed op was a coalescing move on the same selection within about 500 ms, replace `present` instead of pushing to `past` (add `history.replacePresent`). Use a timestamp passed in the action (not `Date.now()` in the reducer) to keep it pure and testable. Any other action (rotate, delete, select, undo) breaks the chain. Inspector arrow buttons keep one step per click (A12). Pointer drag is always one step. Note the net effect of a burst that returns to the origin (a no-op step): it is acceptable, but cheap to drop if `present` equals `past[last]` (not required).
6. Shortcut list: a visible, always-on panel below the Inspector in the right column (e.g. a `<details>` "Keyboard shortcuts" disclosure, closed by default, per the SIM-015.7 plan, or open on wide screens), rendered from one `SHORTCUTS` const in `src/ui/copy/roomlayout.ts` (D36) (`{keys, action}[]`) so the list and the handler table cannot drift (tested: every `keyAction` binding appears in the list). Show Cmd on macOS only if trivial; otherwise "Ctrl/Cmd+Z". Use `<kbd>` and a real `<dl>` or table. Also set `aria-keyshortcuts` on the Rotate, Delete, Undo and Save buttons.
7. A11y and announcements: the click layer stays `aria-hidden` (Items list remains the AT path). The canvas region needs an accessible description pointing to the shortcut list (`aria-describedby`). Announce via the existing `role="status"` line: extend `done.moved` with a count/position only if short (e.g. "Moved 3 items." / "Moved to tile 4, 2."). A burst of arrow presses will chatter in a live region, so keep `aria-live="polite"` and let the coalesced notice just replace the text (the same string repeating is not re-announced, so include the position). Marquee: announce "3 items selected" (reuse `inspector.count`) via the status line, since the Inspector heading is not live. Refusals should be `role="status"` as today (not alert: they are not errors). Do not rely on colour for ok/refused ghosts: dashed vs solid already differs. Respect `prefers-reduced-motion` (no animation is planned; do not animate the snap-back).
8. Tests: state-machine table tests (click vs drag threshold, shift, cancel, pointercancel, out-of-room clamp where `canvasTile` returns null: treat as unchanged last tile, not a drop). `keyAction` table tests (inputs, dialog, Mac meta, repeat keys; `e.repeat` is fine for arrows but not for R/Delete, so ignore repeat there to avoid double rotate). Reducer tests for `selectMany` and coalescing (same selection merges, different breaks, timeout breaks, undo count). Extend `LayoutEditorViews.test.tsx` for the list.

## Risks
- A drag that starts on an item while the tool is armed must not start a drag (wrong mode); guard on `tool`.
- Wrapper `onKeyDown` also receives keys from dialog contents and form controls; the target filter is essential or Backspace/Delete in the size form would delete items.
- Ctrl+S: browsers fire the page save if preventDefault is missed; handle in keydown, not keyup.
- Coalescing with a time window makes undo non-deterministic for users; prefer the "same key-burst" rule (consecutive arrow keydowns with no other action between, and a window of about 1 s) and document it in the shortcut list.
- Ghost verdict via `moveItems` on every rAF for a large selection: it is O(items), fine for 20+ seats; memoize on `(dx,dy)` so it recomputes only on tile change.
- `canvasTile` returns null outside the room; a drop outside must be treated as cancel (no notice), or as refused out_of_bounds. Decide explicitly.
- Delete with a mixed selection (seats + fixtures): the reducer refuses the whole op. Check this is intended or delete only the fixtures (the current behaviour is refuse-all, which is simple; keep it).
- Scroll container: pointer coordinates must account for scroll (`getBoundingClientRect` on the click layer already does, since it is inside the scroller). Edge autoscroll while dragging is out of scope; say so.

## Open questions
1. Drop outside the room or on a refused tile: silent cancel or the refusal message? (I recommend a message for refused tiles, silent for outside.)
2. Should Esc with nothing armed clear the selection? (I recommend yes, as the lowest priority.)
3. Shift+Arrow for 5-tile moves: in or out? (I recommend out.)
4. Shortcut list: open by default on desktop, or a closed disclosure? (I recommend a disclosure, closed, plus the `aria-describedby` link.)
5. Coalescing window: 500 ms vs. "until any other action"? (I recommend any other action, plus a 1 s idle limit.)
6. Should tray seats (unplaced) appear in the marquee or in drag? (They are not on the map, so no.)
