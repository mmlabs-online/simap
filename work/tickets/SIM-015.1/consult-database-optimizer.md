## Findings

Baseline (what the migration builds on)
- Only two migrations exist: init `db/migrations/20261120150000_init.sql` and `20261120190000_members_profile_confirmed_at.sql`. The README rules (`db/migrations/README.md:6-16`) are: forward-only, no `begin/commit`, no `create index concurrently`, no `grant`, every prefix must work with the previous image, and R6 (every unique key and FK includes `org_id`).
- Free-form geometry today: `seats.x/y/rotation` are `double precision not null default 0`, `w/h` are nullable (init.sql:88-92). `layout_fixtures` has the same columns, plus `kind` with a 10-value check (init.sql:169-186) and `label`. `rooms` has no size (init.sql:60-75).
- The previous image inserts seats without any placement columns (`src/server/rooms/rooms.db.test.ts:166`; `scripts/schema-check.mjs:171`). It also updates rooms, and the seeder inserts seats and fixtures with only x/y (`db/seeder.js:99-129`). So every new column must be nullable or carry a default, or old-image inserts break.
- `layout_fixtures.kind` is a closed set (door, window, room, stairs, elevator, server, cabinet, pillar, blocked, label). It has no plant and no wall, but LAY-03 (`docs/spec-v1.md:349-351`) lists plant and wall. The manifest `src/lib/sprites/keys.json` has plant.large, wall.*, whiteboard and others. A sprite key therefore does not map 1:1 to `kind`.
- The manifest has `tiles: [w,h]` (null for avatar, device and state sprites that are not placeable), `blocks`, and a `layer` (floor, wall, furniture, overlay). Direction variants such as `desk.pair.e/n/s/w` and `door.*` are separate keys, and for `.e`/`.w` the footprint is swapped (`desk.single.e` is [1,2] and `desk.single.n` is [2,1], keys.json:178-209). Some keys have no direction and are meant to be rotated (`table.coffee` [2,1], `sofa`, `elevator`, `stairs`, `shelf.books`, `whiteboard`, `window.double`).
- Footprint under rotation therefore comes from two sources: a directional key already swaps tiles, while a non-directional key is rotated by the `rotation` column. Rotation 90 or 270 swaps w and h only for non-directional keys. This ambiguity must be settled in the plan, because it decides the footprint the validator computes.
- There is no `seats.kind` or sprite column, and seats are created by `src/server/rooms/rooms.ts` (seat_counter, D30). The seat sprite key must be a desk or chair group.
- A seat's footprint is its desk sprite. `desk.single.*` and `desk.pair.*` are the 1×2 and 2×2 desks. A 2×2 `desk.pair` raises the question whether it is one seat or two (LAY-02 says one desk is one seat, so it is one). The chair is probably a separate decoration or a fixture, not part of the seat footprint.
- Locking convention already exists (`src/server/rooms/rooms.ts:213-224`): the room row first (`for update` for create, delete or rename), then seats in ascending id order, then devices and requests. The layout save has to follow this order.

## Recommendations

1. One expand migration, e.g. `20261122xxxxxx_room_tile_layout.sql`. It adds columns and constraints only and drops nothing (R2; the init x/y/rotation/w/h stay for a later contract). Do not reuse the old column names (x, y, rotation), because a type or meaning change would break the previous image. Use new names.
   - `rooms`: `grid_w integer null`, `grid_h integer null`, `layout_version integer not null default 0`. Add `check ((grid_w is null) = (grid_h is null))` and `check (grid_w between 1 and 64 and grid_h between 1 and 64)`. The upper bound is the plan's call (a cap such as 64 keeps the overlap check cheap). Do not store a default size on existing rows: null means "no saved layout". GET computes the usable default (derived from seat count, per the "usable default" AC) and never writes it.
   - `seats`: `tile_x integer null`, `tile_y integer null`, `tile_rotation smallint null`, `sprite_key text null`. Add `check ((tile_x is null) = (tile_y is null) and (tile_y is null) = (tile_rotation is null) and (tile_rotation is null) = (sprite_key is null))` so placement is all or nothing. Add `check (tile_x >= 0 and tile_y >= 0)` and `check (tile_rotation in (0,90,180,270))`. Null means "unplaced", and an unplaced seat stays reachable through the GET default (AC 3).
   - `layout_fixtures`: the same four columns, `tile_x/tile_y/tile_rotation/sprite_key`, nullable with the same all-or-nothing check, because old-image inserts (including the seeder) only set kind/x/y. Keep `kind` as is. The new sprite_key for placed rows is validated by the manifest in `src/lib`. If the plan wants to accept plant or wall fixtures, `layout_fixtures_kind_check` must be widened. The existing constraint is named, so change it as drop plus add with `not valid`, then `validate constraint` in the same file (or a later one). A widening is safe for the old image. Decide whether `kind` is derived from the sprite group on save or whether the check is dropped in a contract step.
   - Do not backfill placement for existing seats in the migration (old rows have free-form pixel x/y, and there is no data to convert reliably). Leave null and let SIM-015.2 or the first save place them. A deterministic auto-flow in GET is an option, but the default must not be persisted until a save.
2. Bounds against the room size cannot be a column CHECK (it needs another table and a sprite footprint). Enforce it in the validator and re-check it in the save transaction with the room row locked. Put only row-local rules (non-negative, four rotations, all-or-nothing, sprite_key not blank) in DB checks.
3. R6 and integrity: no new tables are needed, so the existing composite FKs and `unique (org_id, id)` already apply. If a table is ever added (e.g. a layout-revision table), follow init.sql conventions (`org_id not null`, unique `(org_id, id)`, composite FK, indexes starting with `org_id`) or `pnpm schema:check` fails (`scripts/schema-check.mjs:62-82`). Every save query must filter `org_id = $1` and `room_id`, and the PUT must verify every submitted seat id belongs to this room and org by selecting the room's seats `for update` and comparing the id set. Reject any id not in the set with 422 (AC 5).
4. Indexes: the existing `layout_fixtures_org_room_idx (org_id, room_id)` (init.sql:187) and the `seats_org_room_seq_key (org_id, room_id, seq)` cover the room-scoped reads. No new index is needed for read-by-room. Do not add a DB unique index on `(org_id, room_id, tile_x, tile_y)` (see 5).
5. Overlap split between DB and validator:
   - A multi-tile sprite occupies a rectangle (anchor tile plus footprint), so a unique index on the anchor tile cannot catch overlap. It would also falsely reject legal stacking such as a floor tile under a desk, or a non-blocking fixture on a seat tile. Do not try to enforce overlap in the DB. An `exclusion` constraint with a box type needs a stored footprint, `btree_gist`/`create extension` (Ming's step, README:9-10) and manifest data in the DB. Not worth it for v1.
   - The validator (`src/lib/validate`) does it: compute each item's rectangle from the manifest (tiles, swapped for 90/270 where the key has no direction), check it lies inside `grid_w × grid_h`, then reject overlap only between items whose manifest `blocks` is true, and across `layer`. Floor-layer sprites never block. Verify the AC's "wrongly rotated" case: reject rotation for a directional key that does not match its `dir` suffix, or define rotation as ignored for directional keys. Pick one rule and test it.
   - Seats and fixtures are checked together as one set in one pass. Items of seats and fixtures in the same payload are all compared, so a desk cannot sit on a wall.
   - The DB stays the backstop for row-local rules only. State this split in the plan so reviewers do not look for a DB overlap constraint.
6. Concurrency for two Admins saving at once:
   - Take the room row `for update` first (`lockRoom`, rooms.ts:120), then the room's seats `order by id for update`, then delete and insert fixtures, update seats, and update the room size, all in one transaction. This matches the documented lock order (rooms.ts:213-224) and serializes saves per room.
   - That only serializes, so the second saver silently overwrites the first (lost update). Add an optimistic check: `rooms.layout_version` is returned by GET and sent back in PUT as `version`, the save does `... where layout_version = $n` and bumps it, and a mismatch returns 409 (e.g. `layout_conflict`), never 401/403 (R7). If the plan prefers last-write-wins, say so explicitly. I recommend the version, because the editor (SIM-015.2) holds a draft for a long time.
   - Replace fixtures wholesale (delete where `org_id`, `room_id`, then insert the submitted set). It is simpler than diffing, and the fixtures have no inbound FKs. Fixture ids need not be stable, unless SIM-015.2 wants to keep them. Mention it.
   - A save must not touch `seat_counter`, `occupant_id`, status or devices (SEA-02: status derived, `docs/spec-v1.md:235`). Compare the submitted seat id set to the room's set exactly: a missing seat, an extra seat or one from another room or org is refused (LAY-02 creation and deletion are out of scope, ticket.md:36).
   - Authorization (Admin only) and all 401/403 happen in the auth wrapper before the transaction (R7). Domain refusals (out of bounds, overlap, bad rotation, unknown sprite, foreign seat, version mismatch) are 422 or 409 and roll back everything (AC 5).
7. Tests: unit tests for the validator (bounds, rotation, unknown key, footprint swap, blocking overlap vs non-blocking, same-tile seat plus fixture). DB tests (`pnpm test:db`): cross-org id refusal, atomic rollback on a bad item, round trip after save, concurrent save conflict with two clients, the old-image insert shape still working (insert a seat with only the init columns), and a `schema:check` case for each new constraint (`scripts/schema-check.mjs` has the pattern). Update `db/migrations/README.md` schema section (:18-40) in the same ticket. Update `db/seeder.js:99-129` only if the seeder should show placed data. It still works unchanged.

## Risks

- Footprint under rotation (directional vs non-directional keys) is the biggest ambiguity. A wrong rule in the validator saves layouts the renderer in SIM-015.3 draws differently. Pin it with the manifest tests and document it once.
- A widened `layout_fixtures_kind_check` or a `not valid` constraint must be forward-compatible with the old image. An old image never writes the new columns, so a placed fixture with a stale `kind` is the only hazard. Keep `kind` and `sprite_key` consistent in the save.
- Adding `check` constraints with a plain `alter table ... add constraint` on a populated table takes an ACCESS EXCLUSIVE lock and a scan. The tables are small in v1, so acceptable, but use `not valid` plus `validate constraint` if the plan wants less lock time (the runner uses one transaction per file, README:8).
- Rows of old seats stay unplaced after migration, so GET's default layout must always return them, or seats become unreachable (AC 3). It must be deterministic and never saved without a PUT.
- Manifest drift: sprite keys are validated against `src/lib/sprites/keys.json` at save time, but stored keys can later disappear when art is replaced (D45). SIM-015.3 must tolerate an unknown stored key. No FK is possible for it.
- Without the version check, two Admins lose edits silently. With it, SIM-015.2 must handle 409.
- High path (`db/migrations/**`), so the plan needs Ming's approval (ticket.md:52).

## Open questions

1. Should seat footprint come only from the desk sprite_key, and is the chair a separate fixture or an overlay? Is a `desk.pair` one seat (LAY-02 says yes)?
2. Directional sprite keys: is `rotation` redundant for them (so reject a mismatch), or should rotation be the only source and non-directional keys the rule?
3. Do we accept optimistic `version` (409 on stale), or last-write-wins after the lock? I recommend the version.
4. Room size limits (max grid, min grid) and the default size for a room with no saved layout (derived from the seat count?).
5. Widen the fixture `kind` check for plant/wall, or derive `kind` from the sprite group, or drop it later in a contract step?
6. Should the PUT keep the fixture ids stable, or replace them wholesale?
7. Should the room size be allowed to shrink below placed items (refuse, or refuse only if blocked)? The validator refuses any out-of-bounds item in the same payload, so shrinking works only if the same PUT also moves the items.
