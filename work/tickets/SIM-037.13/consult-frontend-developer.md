## Findings
- DevicesPage (src/ui/devices/DevicesPage.tsx) wires 6 dialogs through 7 useState slots (`transferring`, `returning`, `extending`, `takingBack`, `placing`, `holding`; form/deleting stay on the list). Handlers are in one `actions` memo (DeviceRowHandlers). `onCancelHandoff` is async (acting ref, cancellingId busy, `cancelOutcome`). Each dialog `onDone` does: close, set notice, refresh, then focus the h1. Refresh and notice are coupled to list-only state (`refreshAll` also refreshes 3 handoff lists, the overdue list, the nav badge, `filter`).
- Dialog props: Transfer, Return, Extend and TakeBack take `device|null` (mounted while non-null), with `onClose`, `onStale`, `onDone(device)`. Place and Assign take `open`, `device`, `mode`. Assign `onDone(mode)` gives no notice. Place `onDone()` gives no notice. Copy for notices exists: `devicesCopy.transfer.sent`, `giveBack.sent`, `extend.sent`, `takeBackDone(device, filter)`, `cancelOutcome(result, device, kind)`.
- `rowActions(device, handlers, busyId)` already gates by server flags (canTransfer, canReturn, canAssign, canEditHolding, canTakeBack, pendingHandoff.canCancel, mine&&overdue&&!pending for extend, `placeModes`). Passing only the 8 non-edit/delete handlers gives "exactly the flags allow". Edit and Delete are omitted by leaving out `onEdit`/`onDelete`.
- Detail page: `useDeviceDetail` only has `retryDetail`/`retryHistory`, and both dispatch `load`. That resets state to `INITIAL_DETAIL` (status loading, device null), and `INITIAL_HISTORY` likewise. Using these as the refresh would blank the page, unmount the h1 and the dialogs (device is null), and lose loaded history pages. A silent refresh is needed.
- The h1 is focused once on first ready (`focused` ref). `DeviceDetailView` has no notice slot and no actions slot. The h1 is rendered in several states.

## Recommendations
1. **Do not extract a full `useDeviceDialogs`.** The two pages differ in refresh and notice (list refreshes 5 things, and its notice/focus logic and filter-dependent `takeBackDone` are list-specific). Extract a small shared piece instead: `useDeviceDialogState()` returns the 6 slots plus an `open*` handler set (the setNotice(null)+setX parts of `actions`) and a `<DeviceActionDialogs state api seatsApi roomsApi onDone(kind, device) onStale />` component that renders the 6 dialogs. Each page supplies `onDone`/`onStale` callbacks (refresh strategy, notice, focus). This removes about 100 duplicated lines without changing list behavior. If a refactor of DevicesPage is judged out of R4 or too risky, fall back to wiring again on the detail page (about 90 lines) and log a follow-up. The extraction is cheap if DevicesPage tests stay green, so I lean toward extracting. Add a pure `doneNotice(kind, device, filter?)` helper (Transfer, Return, Extend, TakeBack) in a `.ts` file so both pages and tests share it.
2. **Silent refresh in `useDeviceDetail`.** Add a `refresh()` that bumps the counters and dispatches new events `reload` / `reloaded` (or `loaded` with a `keep` flag). It does not reset to loading, and it keeps the current device if the call fails (or surfaces an error notice). The history refresh replaces the first page, drops the extra pages and resets nextCursor (acceptable, state it). Run both with `Promise.all`; resolve after both, then focus. Add reducer tests for: refresh keeps device while in flight, a stale answer is dropped, and a failure keeps the old data.
3. **Notice and focus.** Add `notice?` and a slot (or children) to `DeviceDetailView`, placed after the h1 (or below the back link) so it is also present when the device is gone. Reuse the DevicesView pattern: a persistent `<div aria-live="polite">` that is always mounted, with `<p role="status">` or `<p role="alert">` inside. Focus: after `refresh()` resolves, `headingRef.current?.focus()` in a post-commit effect or after the awaited promise (h1 has tabIndex -1). Prefer a `focusRequest` counter state plus `useEffect`, as DevicesPage does with `focusTarget`, so it hits the new node. Clear the notice when any dialog opens (as the list does). Assign and Place give no notice in the list; for detail add notices only if copy exists (open question), otherwise keep silent but still refresh and focus. Place and Assign edit modes keep the button, so focus the h1 for assign, not for edit-holding (mirror the list).
4. **Gone and not-allowed states.**
   - After transfer, return, take-back, cancel: the device still exists, so refresh and show it (transfer or return becomes a pending handoff; flags change, buttons update). Take-back shows the "filter hint" suffix only for list filter `placed`; pass `"all"` on detail.
   - If the refresh returns `not_found`, the reducer already goes to `notFound` (h1 "not found") and the notice still shows in the aria-live region; focus the h1. Make the live region sit outside the status branches.
   - Dialog `onStale` (flags changed under the user): silent refresh, no focus move.
   - Action dialogs must not unmount mid-flow because of the refresh: `device` for a dialog comes from its own state slot (set on open), not from `detail.device`, as on the list.
   - `onCancelHandoff`: copy the list's acting ref, busyId (`device.id`) to disable the buttons; use `cancelOutcome(result, device, pending.kind)`; refresh only if `outcome.refresh`.
   - While `detail.status !== "ready"` render no actions; hide actions while a silent refresh is in flight (or disable via `busyId`) to prevent double submit.
5. **Actions placement.** Render `<DeviceRowActions device handlers busyId>` in `DeviceDetailView` via an `actions?: React.ReactNode` prop (keeps the view pure), under the h1 in the ready branch. `hasAnyAction` is not needed; DeviceRowActions already renders null when empty.
6. **Testability (node, no DOM).**
   - Pure helpers with unit tests: `doneNotice`, the refresh reducer events, a `handlersFor(open)` factory if extracted, a focus-effect decision helper.
   - `renderToStaticMarkup` of `DeviceDetailView` with actions and a notice props: asserts action gating per flags (owner with canTransfer shows Transfer; plain viewer shows none; Edit and Delete never), the live region exists when the notice is null (always mounted) and has role status or alert, and notFound still renders the notice.
   - The existing `rowActions`/`device-actions.test.ts` already cover gating; add a case for the detail handler set (no onEdit/onDelete).
   - The dialogs already have static-markup tests. Refresh, focus and notice flows cannot be run without a DOM, so write them as pure functions (outcome to {notice, refresh, focus}) and say so in the plan. The ticket test plan "Component: refresh + notice + focus after done" needs to be reworded to "pure helper + static markup" (flag to Ming).
7. **Size.** M (not S): about 150-200 lines product (hook state + dialog component + refresh reducer/hook + view slots + page wiring), 150-250 lines tests; DevicesPage shrinks by about 100 if extracted. Fits one cycle if the DevicesPage refactor is mechanical. If the reviewer wants zero risk to the list, do the fallback (rewire, no refactor) and the size is smaller but the duplication is a follow-up.

## Risks
- `retryDetail` reuse would blank the page and drop focus; must add silent refresh.
- Extracting from DevicesPage touches a heavily-used page (regressions in focus/notice order); keep its `onDone` bodies in the page, share only state and rendering.
- Starting transfer, return and extension depends on the handoff start bug fix (SIM-037.6 PR #102); confirm it is merged, or the dialogs fail on the detail page too.
- Stale `device` for dialogs: if dialogs are driven from `detail.device`, a refresh swaps the prop mid-dialog. Keep the snapshot.
- History reset to page 1 after an action discards "load more" pages (minor UX).
- Double submit while the refresh is in flight; R7 (401/403 re-send) is not affected as no new routes are added.
- `takeBackDone` expects a filter; passing a list filter on detail is meaningless.
