## Findings

**Current state (src/app/globals.css, src/app/layout.tsx)**
- Tokens: about 60 MD3-style custom properties in `:root` plus a `[data-theme="dark"]` block, mapped by one `@theme inline` block (`--color-primary`, `surface-low`, `on-surface-variant`, `outline`, `accent-orange`, `status-*`, `px-*`, `--radius-md3*`, `--ease-md3`). A separate `--aw-*` palette (8 vars, light and dark) feeds `.aw-*` classes (~320 lines of plain CSS, with hard-coded px, hex and shadows).
- Name collision: the brief uses `--color-surface`, `--color-border`, `--color-focus`, `--radius-*`, `--shadow-*` and `--font-family-*`. Today `--color-surface` is an `@theme inline` alias of `--surface`. If `tokens.css` defines `--color-surface` in `:root` while `@theme inline` also defines it, the two fight. Also, `--text-hero`/`--text-h2` (80 px, 30 px) are plain vars, and `.text-hero` is a class.
- **Mapping rule for Tailwind v4:** `@theme` generates utilities only from `--color-*`, `--radius-*`, `--shadow-*`, `--font-*`, `--spacing`, `--breakpoint-*`, `--text-*` and similar namespaces. Because dark mode switches variable values, use `@theme inline` (or reference vars) so utilities follow `[data-theme=dark]`. Do not use a plain `@theme` with literal light hex values, or dark will not switch.
- **Spacing:** Tailwind v4 uses `--spacing: 0.25rem`, so `p-4` is already 16 px and matches the brief's 4 px base. Do not redefine `--space-*` as utilities. Keep `--space-*` as plain vars for CSS, and map only the odd ones (`p-3.5`, `gap-1.5` stay off-scale; snap them).
- **Radius:** the brief defines `--radius-sm/md/lg/xl/2xl/full`. In `@theme` these override Tailwind's `rounded-sm|md|lg|xl|2xl|full` (default 2px/6px/8px/12px/16px). Only `sm` changes (2 → 4 px), `md` 6 and `lg` 8 are unchanged, and `xl` and `2xl` already match. Existing `rounded-md3*` (10/12/16/20 px) and `rounded-full` pill buttons need a decision. The brief says buttons are `--radius-lg` (8 px), not pills. That is a visible change to every Button, IconButton, Chip and nav item.
- **Colour migration:** the brief palette has no tonal containers (`primary-container`, `error-container`, `tertiary-container`). Badges need new derived tint backgrounds. The brief gives only the text colours (success, warning, danger, info), so the planner must define tint backgrounds per theme. Today `--primary` is near-black (#1c1c1c) and used by `bg-primary`; the brief's `text-primary` utility name collides with the "primary" semantic. Per the brief, `text-primary` should resolve to `--color-text-primary`, and the old `--color-primary` must go.
- **Fonts:** `layout.tsx` loads Manrope via `next/font/google` (`--font-manrope`, latin+vietnamese) and Fraunces (`--font-serif`, `preload: false`). Manrope is referenced in `globals.css` in 5 places (`@theme` x3, `body`, `h1-3`, `.font-heading`). Swap to `DM_Sans({subsets:["latin","latin-ext"], variable:"--font-dm-sans", display:"swap"})`. DM Sans has no Vietnamese subset in `next/font/google` on some versions; verify. The `latin-ext` subset covers most Vietnamese letters, and the app is English-only per D36, but user names may contain Vietnamese diacritics, so check the glyphs. If DM Sans lacks them, the fallback stack matters. `@theme inline { --font-sans: var(--font-dm-sans), ... }`. The brief's `--font-family-sans: "DM Sans"` would not resolve to the next/font hashed family, so define `--font-family-sans` as `var(--font-dm-sans), sans-serif`. Drop the Manrope-based `--font-mono`: the brief wants `ui-monospace`. Keep the Fraunces `--font-serif` as is. The Google Fonts `<link>` for Material Symbols stays (CSP unchanged). `next/font` self-hosts, so no CSP change.
- **Hard-coded values (src, non-test, grep):**
  - Tailwind arbitrary values (`rounded-[`, `shadow-[`, `text-[`, `[Npx]`, `min-h-[`, `w-[`, `h-[`, `font-[`, `rounded-md3`): **128 hits in 56 files**. Worst: `AppShellView.tsx` (12), `EntityFormDialog.tsx` (9), `Button.tsx`, `Chip.tsx` (4 each), `CheckinPopup`, `SeatsView`, `SpriteBrowser`, `MapItemEditor` (5 each).
  - Hex in `ts/tsx`: 78 hits in 24 files, but most are tests or pixel/sprite/canvas code (`src/lib/sprites/avatar.ts` 14, `overlay.ts` 5, `src/ui/roomlayout/paint.ts` 2, `photo-canvas.ts`, `Avatar.tsx`, `group-form.ts` 2). The non-pixel ones to check: `Avatar.tsx`, `group-form.ts` (group colour data, probably user data, so exempt). The grep test needs an allowlist for sprite and canvas code (out of scope per the ticket) and for tests.
  - `rgba(`, `shadow-[`, inline colour styles in `src/ui` non-test: 21 hits in 14 files (`SeatOverlay.tsx` 4, `paint.ts` 2, `Button`, `Card` 2, `EntityFormDialog` 2, `CheckinPopup`, `AppShellView` 2).
  - Uses of old colour utilities (`bg-primary`, `bg-accent-orange`, `text-primary`, `bg-primary-container`): 52 hits in 39 files. The full old-name utility surface (`surface-*`, `on-surface*`, `outline*`, `secondary-*`, etc.) is much larger, so the sweep touches most UI files. A codemod (sed map of old class names to new) is the realistic approach, not hand edits.

- **Breakpoints, md 768 → 800:**
  - Tailwind default `md` is 768. `@theme { --breakpoint-md: 800px; --breakpoint-lg: 1024px; --breakpoint-xl: 1280px; }` is needed. `lg` and `xl` already match Tailwind defaults (1024/1280). Only `md` changes.
  - **`md:` usage:** only 15 hits in 11 files (`DeviceTable` 2, `IncomingTransfers` 2, `PendingExtensions` 2, `PendingReturns` 2, `OverdueBanner`, `Button` 1, `AuthLayout`, `SignInScene`, plus `credentials.ts`/`verify.ts`/a test that are not breakpoints). Low blast radius: 768 to 800 shifts the tablet-portrait band only. Affected screens: devices table/lists, device pending panels, sign-in scene.
  - **Important:** the shell uses `lg:` (1024), not `md:`, for the sidebar. The nav rail is `lg:w-[88px]` at ≥1024 and a bottom bar below. The brief says the sidebar (216 px) appears from `md` 800. So the shell breakpoint changes from `lg` to `md` and the width from 88 px rail to 216 px: this is a layout change (labels beside icons, content area narrower), not just a token swap. It touches `AppShellView.tsx` lines 51-213 and everything that assumed 88 px (content padding, sticky offsets, the room map and layout editor width). Ticket open question 2 needs Ming's answer.
  - JS media queries hard-code 768/1024/1280 (not Tailwind): `SignInScene.tsx:9` `(min-width: 768px)` must become 800 to match `md`; `LayoutEditorPage.tsx:22` 1024 (OK); `SmallWorld.tsx:27` 1280 (OK, and `SmallWorld.test.tsx:123` asserts the string). CSS `@media (max-width: 639px)` and `min-width:1280px` in `globals.css` are untouched. Suggest exporting the three queries from one `src/lib/breakpoints.ts` to avoid drift.
- **Motion:** there is a global reduced-motion rule in `globals.css` (sets durations to 0.001ms) that covers CSS, but canvas/JS motion (`src/lib/sprites/walk.ts`, `idle.ts`, `ui/roomlayout/WalkLayer.tsx`, `useWalks.ts`, the sign-in `SmallWorld`) needs a check. `useReducedMotion.ts` exists in `roomlayout`; verify that every JS-driven animation uses it (including the sign-in walker and check-in). The brief's `.animated-character { animation: none }` has no matching class today; add or skip. `--duration-ui` 150 ms matches the existing `duration-150` and the `0.14s` state layer.
- **Focus ring:** current ring is `outline 2px var(--primary)` plus a 3 px orange-tinted box-shadow. The brief wants a 2 px `--color-focus` (#7A915C) ring with offset. #7A915C on white is about 3.5:1 (OK for non-text 3:1 per WCAG 1.4.11), but on `--color-canvas` and especially on a coral button it is weaker, so check. In dark mode the derived focus colour must stay at 3:1 or more.
- **Contrast pre-check (light, computed roughly):** white on `#ED5B35` is about 3.4:1, which fails AA for 14 px/500 text (needs 4.5:1; large-text exception needs 18.66 px bold or 24 px). White on hover `#D94B26` is about 4.1:1, which also fails. This is a real conflict between the brief colours and its "white text, Label style 14/20 500" button spec. White on `#4D6540` is about 6.4:1 (OK). `--color-warning` #855C15 on white is about 5.9:1 (OK). `--color-info` #45648F is about 5.9:1 (OK). `--color-danger` #B44C46 on white is about 5.0:1 (OK, but near the limit on tint backgrounds). `--color-text-secondary` #475569 is fine on white and canvas. Verify with a real tool in the plan. Options for coral: use dark text (#272931) on coral (about 5.2:1), darken the button to about #C8401C for white text, or keep the brief and record it as a known AA exception for Ming. Needs a decision.
- **Dark values to derive:** every colour token (workspace/pixel primary and hover, canvas, surface, cream, tile, 3 text, border, divider, focus, 4 feedback, 2 room colours). Pixel `--px-*` already has its own dark overrides (keep). Room-map floor/green are used by canvas painting (`paint.ts`), so check that they are read from CSS vars or constants.

## Recommendations

1. **Token files.** Create `src/styles/tokens.css` with all brief vars in `:root` (light) and `[data-theme="dark"]` (dark). Name plain vars so they do not collide with Tailwind namespaces: give the colours the brief's `--color-*` names, but put them only in `tokens.css`, and have `globals.css` `@theme inline` reference them only for utilities that need a *different* name (`--color-canvas`, `--color-text-primary` → `text-text-primary` is ugly, so also map the short alias `--color-ink: var(--color-text-primary)` if wanted). Simplest: because the brief's names already start with `--color-`, define them directly inside `@theme` (not `inline`) in `tokens.css`, and put the dark overrides in `[data-theme="dark"]` re-setting the same `--color-*` vars. Plain `@theme` emits the vars on `:root` and utilities use `var(--color-x)`, so an override in `[data-theme=dark]` does work, as long as the override is set on `html`. Verify this once in the first slice. The `@theme inline` variant is the fallback. Import `tokens.css` from `globals.css` right after `@import "tailwindcss"` (Tailwind needs `@theme` in the file graph it processes), and also satisfy the brief's "imported at app root" via `layout.tsx` importing `globals.css`.
2. **Compatibility layer first, then delete.** Keep every old token name alive for slice 1 by re-pointing: `--background → var(--color-canvas)`, `--surface → var(--color-surface)`, `--on-surface → var(--color-text-primary)`, `--on-surface-variant → var(--color-text-secondary)`, `--outline → var(--color-border)`, `--outline-variant → var(--color-divider)`, `--primary` (button fill) `→ var(--color-workspace-primary)`, `--error → var(--color-danger)`, status vars to feedback, `--card-shadow → var(--shadow-card)`, `--aw-*` to cream/pixel tokens. The app then re-themes with zero component edits, so slice 1 is low risk. A later codemod removes the old names and the aliases are deleted in the final slice.
3. **Safe slice order (each slice a PR on `ticket/SIM-071`, green checks per PR):**

   2. UI kit (`Button`, `IconButton`, `Chip`, `Card`, `SectionCard`, inputs `FilledInput`, selects/radios/checkboxes, `EntityFormDialog`, `RoleBadge`, `SegmentedFilter`, `TabBar`, `StatTile`): radius, 44 px min-height, 14 px labels, focus ring, disabled style, status labels. Add kit render tests (classes, 44 px, disabled) and `KitGallery` check. Resolve the pill vs 8 px radius question first.
   3. Shell and sidebar (`AppShellView`, `PageHeader`, `RoomSwitcher`, container widths 1320/1600) including the 216 px sidebar and `lg` → `md` switch, only after Ming confirms question 2. Check the room map and the layout editor, which depend on the content width.
   4. Management screens (members, groups, devices, device types, approvals, audit, dashboard, search, admin, invitations, rooms and seats chrome): mostly mechanical via the codemod; sweep the 128 arbitrary-value hits and 13px/other off-scale sizes.
   5. End-user and pixel surfaces: portal, check-in, room map chrome, `Palette`/`MapItemsView` (pixel green), `PixelLookPicker`, sign-in and `AuthLayout` (`--aw-*` replaced by cream/text-pixel/pixel-primary, `.aw-*` px converted, `--shadow-pixel`), walkers with reduced motion for canvas motion.
   6. Sign-in `.px-card [data-variant="filled"]` (currently orange `--px-btn`) becomes pixel green (`--aw-accent` #3d5a35 is replaced by `--color-pixel-primary`).

## Risks

- **Coral/white AA failure** (about 3.4:1 and 4.1:1) is a direct conflict between the brief's colours and acceptance criterion "Light and dark text/background pairs pass WCAG AA". Must be decided at the plan gate, not silently adjusted.
- **Button shape change** (pill → 8 px) and **sidebar change** (88 px rail at lg → 216 px at md) are large visible differences. Since the brief says to keep the layout, list them as forced differences in the changelog. The sidebar change also moves the breakpoint from 1024 to 800 and narrows the content area on 800-1024 screens (room map, layout editor, tables).
- Name collisions between brief tokens and existing Tailwind/old tokens (`--color-surface`, `--color-primary`, `text-primary`, `rounded-*`, `--shadow-*`) can silently change meaning (for example `text-primary` was near-black, becomes the same text colour, but `bg-primary` buttons would change colour). The alias layer plus a codemod with a before/after class map reduces this.
- Dark mode: derived values on 20+ tokens plus feedback tint backgrounds; contrast must be verified for every pair (a script computing the ratios from `tokens.css` would be better than manual checks, and it can run as a Vitest test).
- Hex check false positives: sprite, avatar and canvas painters, group colour data and test fixtures contain legitimate hex. The grep gate needs an explicit allowlist, or it will be removed or ignored.
- `SmallWorld.test.tsx` asserts the exact media string and `world-palette.test.ts` asserts palette; edits there are allowed only for markup/classes per the ticket, so keep 1280 as is.
- Canvas-based animation (walkers, idle sprites) must honour reduced motion in JS; CSS alone will not stop it. Confirm all of `useWalks`/`WalkLayer`/`idle.ts`/`SmallWorld`/`SignInScene` read `prefers-reduced-motion`.
- Size: roughly 55-60 UI files plus `globals.css`; one PR would be too large to review. The slices above are meant to be independently shippable because of the alias layer.
- DM Sans Vietnamese coverage (member names, Manrope had a `vietnamese` subset).
- R4/R5: the new grep test is "new logic" and needs tests; new dependencies other than DM Sans are out of scope, so write contrast and grep checks without packages.
