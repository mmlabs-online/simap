## Findings (SIM-039.9 consult, frontend)

State of the merged code (what exists and what is missing):
- `src/ui/mapItems/map-items-api.ts` has only `list`, `patch`, `getArtImage`, `reset`. It has no `putArt(key, dir, sprite|null)`, `putImage(key, dir, bytes)` or `deleteImage(key, dir)`. All three are needed. The `call` helper already maps `ApiAccessError` and parses `{error:{code}}`, so each is about 8 lines.
  - `putArt` and `putImage` return the patched `MapItemDto` (`Response.json(r.value)`), so they reuse the `json` reader.
  - `deleteImage` returns 204 with no body. It needs a `read` that returns `{ok:true,value:null}`, because `json` would throw and turn into "internal".
  - `putImage` must send `content-type: image/png` and a body of `Uint8Array`/Blob. The route's `readBytes(req, 65536, "image/png")` enforces the type, and a wrong type or oversize gives 422 `image_not_png`/`image_too_large`.
- Image cache: `createImageUrlCache` in `src/ui/deviceTypes/image-url-cache.ts` is generic (`ImageEntry {id, hasImage, imageVersion}`), and `item-art.ts` already has `itemImageId`/`parseItemImageId`. `useDeviceTypeImages` is the template for the page hook: create the cache in an effect keyed on `api`, `dispose` on unmount (this revokes every URL), `bump` on `onChange`, `sync(entries)` in a second effect. `useCatalogImages` also decodes, but it is tied to the layout. The A10 decision stands: don't reuse it.
  - The 039.8 `getArtImage` already checks `blob.type.startsWith("image/png")`.
  - `load` must be `(id) => { const p = parseItemImageId(id); return p ? api.getArtImage(p.key,p.dir).then(r => r.ok ? r.value : null) : Promise.resolve(null) }`.
- Cache semantics that matter for the page:
  - `sync` drops any id not in the list, so pass entries for every item on the page (all items, or only the open item plus row thumbnails). Row thumbnails make this "all items with any `hasImage`", at most 4 dirs each. That is fine with the cache's limit of 4 concurrent loads.
  - The version stamp makes old blobs invalid. After an upload or remove, use the patched DTO to update the list item in place (or call `reload`), then `sync` again. The new `imageVersion` triggers a refetch automatically.
  - `url(entry)` returns null while loading or failed. The UI cannot tell "loading" from "failed", so the cache needs no change; show a neutral "Image not available" text for both. Adding a failed state would be a scope creep to avoid.
- Page-owned state: `MapItemsPage` keeps the `Dialog` union (edit/reset). The art dialog adds `{kind:"art", key}`. Hold the key and not the DTO, and derive the item from `items.items`. Then an in-place patch refreshes the panel. The current `done()` closes and reloads, so art actions need a different path: replace the item in the list on success. `useList` has `reload` only, so either call `reload()` after each art action (simple, one code path, A2 spirit) or extend it with a local patch. I recommend `reload()` and keeping the dialog open. Check that `useList.reload` does not flip status to "loading" and unmount the dialog; `useMapItems.reload` does set "loading", but `MapItemsPage` uses `useList`, so check that one.
- Upload precheck: `parsePng(bytes)` (`src/lib/validate/png.ts`) returns `{width,height}` without size limits. `validatePng` is device-only (square 24-100), so don't use it. Precheck order, mirroring `checkImageFile`: `file.size > MAP_ITEM_LIMITS.imageBytes` -> `image_too_large`; read failure -> `read_failed`; `bytes.length` recheck; `parsePng` fail -> `image_not_png`; then `mapItemImageFits(item, dir, w, h, px)` -> `image_bad_size`. A pure `checkMapItemImage(file, item, dir)` in `src/ui/mapItems/map-item-image.ts` is easy to unit-test (a fake file with `size` and `arrayBuffer`, as `device-type-image.test.ts` does). `deviceTypes/device-type-image.ts` hard-codes `IMAGE_LIMITS` (100 KB) and device copy, so do not reuse `checkImageFile`; `thumbRendering` is reusable (or copy the idea).
- Existing copy is wrong for maps. `src/ui/copy/api.ts` l.63-68 gives `image_bad_size` the "square, 24 x 24 to 100 x 100" text and `image_too_large` "100 KB". That is the SIM-039.4 A8 problem. Add `mapItemsCopy.art.errors: Record<code,string>` and `art.badSize(wPx,hPx,floor)`, e.g. "This direction needs a PNG exactly 96 x 64 px, up to 96 x 96 px tall" and "32 x 32 px" for floors. `image_too_large` is "64 KB". Map each code through the map copy first and fall back to `apiErrorMessage` (which has `image_changed`, `images_unavailable` and `drive_error`). Server refusals to cover inline: `image_bad_size` (422), `not_allowed` (422, art sprite refused), `image_changed` (409), `item_not_found`/`not_found`, `images_unavailable`, `drive_error`, `unavailable`, and the auth codes.
- Expected size per direction: a pure helper `expectedImageSize(item, dir)` built from `sizeFor(dir, w, h)` and `MAP_ITEM_LIMITS` returns `{w, hMin, hMax}`. Floors are 32 x 32. It is used in both the dialog text and the precheck, and tested against `mapItemImageFits`.
- Package sprite browser:
  - Filter `FRAME_KEYS` by `spriteAllowedFor(item, key) && spriteFits(key, dir, item.w, item.h)`. Both are in `src/lib/map-items/art.ts` and are pure and importable from ui (lib layer).
  - There may be hundreds of frames, so group by `REGISTRY[key].group` and add a text filter. The frame's own `dir` (`RegistryEntry.dir`) is not used by the filters. Don't filter on it (the ticket doesn't ask), but showing it as a label is cheap and helps the Admin choose a south-facing frame. This is an open question.
  - Atlas previews: reuse `loadAtlas({fetch, createImage})` from `src/ui/roomlayout/loadAtlas.ts`, which never throws and returns `{ok:false}` on any failure. That gives the text-only fallback for free. Draw a frame with a `<canvas>` (`drawImage(atlas.image, f.x,f.y,f.w,f.h, 0,0,f.w,f.h)`, `imageSmoothingEnabled=false`, CSS `image-rendering: pixelated`, 2x via CSS width). Note `atlas.manifest.frames` may lack a registry key (A3, `unknown` list), so a missing frame renders as its key text.
  - Load the atlas only when the browser opens, with an `AbortController` for `signal`. Don't put it in `MapItemsLoaded`.
  - Canvas drawing can't be tested under Vitest node env (see Risks).
  - Confirm step: selecting a frame stages it with a preview and "Use this sprite" calls `putArt`. The current sprite is highlighted.
  - "Use library sprite" (`putArt(key,dir,null)`) is disabled when `art[dir].sprite === null`.
- Per-direction panel (a pure view over `MapItemDto`):
  - Dirs = `item.directional ? MAP_ITEM_DIRS : ["s"]`. Floors are `directional:false` per `itemArtDir`; check that the DTO sets this for floors and chairs.
  - Source text: `hasImage` -> custom image; else `sprite` -> package sprite (name the key); else library. The precedence matches `resolveItemArt`.
  - Previews at 1x and 2x pixelated: image via blob URL (`<img style="image-rendering:pixelated">`), package/library via atlas canvas, none via the placeholder look (`#c9ccd1` fill, `#8a8f98` line in `paint.ts`; CSS `bg-[#c9ccd1] border-[#8a8f98]` or a neutral token). Don't import `paint.ts` (canvas, and not in ui->ui? it is ui->ui, so legal, but it needs a canvas draw list). Prefer CSS.
  - The library frame key comes from `libraryItem()` (039.1 A8). For the library preview, `libraryItem(key)` gives the library frame per dir; check how `resolveItemArt` is called with `libraryKey` and whether a helper exists. Otherwise text-only for "library" is acceptable at first.
  - "Images never rotate to fill another direction": do not offer "copy to other directions". The upload input is per `{key,dir}`, and the pure helper must not return anything for a non-allowed dir. The test is `artDirAllowed`.
  - A `<input type=file accept="image/png">` hidden behind a `Button` per dir; reset `input.value` after each choice so the same file can be retried.
- Row additions in `MapItemsView`: an "Art" button next to Edit (props: `onArt`), a "Customised" badge when any dir has `hasImage || sprite`, and a 32 px thumbnail (first dir with an image, else none). The row takes an `imageUrl(item)` function from the hook, as `useDeviceTypeImages` does for Device types. `MapItemsView` is pure and tested with `renderToStaticMarkup`; keep it that way (the thumbnail is just an `<img src>` from props).
- Layering/R1: all of this is ui + lib imports; no server imports. Add the dialog to `src/ui/index.ts` only if needed (the page is already exported).
- R7/api: `apiFetch` re-sends once on 401/403, and image PUT is idempotent in effect, so there is no issue. Body is a `Uint8Array`; make sure `RequestInit.body` typing (`Uint8Array<ArrayBuffer>`) works as in `device-types-api`'s `putImage` (copy that signature).

## Recommendations
1. API client (AC1): add `putArt`, `putImage`, `deleteImage` to `map-items-api.ts` and tests in `map-items-api.test.ts` (method, URL encoding, headers, 204 handling, error codes, `ApiAccessError` mapping).
2. New pure modules, all unit-tested in node env:
   - `map-item-art.ts`: `artDirs(item)`, `artSource(item, dir)`, `expectedImageSize(item, dir)`, `packageSprites(item, dir)` (filter + group + text query), `imageEntries(items)` (`MapItemDto[]` -> `ImageEntry[]`, per A10: all four dirs for directional items, `s` for others, `hasImage` and `imageVersion` straight from the DTO).
   - `map-item-image.ts`: `checkMapItemImage(file, item, dir)`; `mapItemImageMessage(code, item, dir)`.
3. `useMapItemImages(api, items)` hook modeled on `useDeviceTypeImages` returning `(key, dir) => string | null`.
4. Components: `MapItemArtDialog` (native `<dialog>`, like the form dialog; direction panels as `section` with `h3`), `SpriteBrowser` (`useAtlas` effect with the fallback), a `ArtPreview` component. Keep `MapItemArtDialogBody` exported and pure for static-markup tests, as `MapItemFormFields` does.
5. Errors: one `role="alert"` line per direction panel (so errors show inline in the right place), cleared on the next action. `image_changed` -> reload the item and show the message. `images_unavailable`/`drive_error` go in the art panel only, never in the page-level list error.
6. Copy: `mapItemsCopy.art` (title, direction labels North/East/South/West per A5, source texts, buttons, per-code errors, sprite browser strings, atlas fallback note) in `src/ui/copy/mapItems.ts`.
7. Remove-image: no confirm (A5 of 039.6). Upload replaces without a confirm. Don't offer "Remove" when `hasImage` is false.
8. Don't edit `src/lib/**` or `image-url-cache.ts`; nothing there needs to change.

## Risks
- Size: the 039.6 estimate was ~500 product lines (dialog 180, browser 150, image check+copy 60, cache hook 60, API 40, copy 40). From what exists now it looks right: the cache and `loadAtlas` already exist, which saves roughly 60 lines. Expect ~450 lines product plus ~350 test. It fits one implement/review cycle if kept as above, but it is on the high side of the 400 guide. A natural cut if the reviewer objects: move the atlas previews (canvas) to a follow-up and ship the text-only browser. That is already a required fallback, so it is a low-risk split.
- Canvas/atlas preview cannot be unit-tested in Vitest node env (no DOM, no canvas). Mitigate by keeping the logic pure (frame rect computation, filter, grouping) and testing only that; the canvas component is manually verified. State this in the plan so R5 ("new logic has tests") is satisfied honestly. Do not add jsdom.
- Hooks/effects (cache hook, atlas load) are also untestable in node env except via the pure cache (`image-url-cache.test.ts` already covers it). Keep the hook thin.
- Staleness: the dialog derives the item from the list. If the list reloads to "loading" it could unmount the dialog; confirm `useList.reload` keeps the old items. Also a late `getArtImage` response after an upload is handled by the version check.
- Blob revocation: row thumbnails and dialog previews must use the same cache instance (one hook at page level), or URLs revoked on dialog close would break the rows. Revoke only on page unmount.
- Mid-session size change: slice 1's size change deletes images server-side; after any `patch`/`reset`, `done()` already reloads the list, and `sync` then drops the images (`hasImage:false`). Good, no extra work.
- A8 copy: `apiErrorMessage` is shared with device types, so don't edit its device wording. The map-specific copy must win in the art panel. A test that the map message differs from the device message for `image_bad_size`/`image_too_large` guards it.
- File input: reading the file in the browser with `File.arrayBuffer()` is fine. `accept` is only a hint; the check ignores type and name (as with device types).
- Stale chair art: `chair.office` is not placeable and is hidden from the palette, but it is in the list (A9). Its art does apply (A2 of 039.8). It is `directional`? If the DTO says `directional:true` for the chair, all four dirs show; verify `LIBRARY_ITEMS` for `chair.office` and the floors before writing tests (not checked here).
