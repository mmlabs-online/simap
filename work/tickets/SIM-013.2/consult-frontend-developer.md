## Findings
- The device API and types are ready (`src/lib/devices/types.ts`). `DeviceDto` is `{id,name,type,inventoryNumber,mac,owner{id,displayName},placement|null{seatId,seatCode,roomId,roomCode,role},mine,canEdit,canPlace}`. The list response is `{items, truncated}`, with a cap `DEVICE_LIMITS.list=1000`. `?placement=all|placed|inventory` is parsed by `parseDeviceQuery`. Note that `canPlace` is not `canMove`.
- `src/lib/validate/device.ts` exports `normalizeMac`: a blank gives null, an invalid value gives undefined, and a valid one gives lowercase colon form. It also exports `validateDeviceCreate` and `validateDevicePatch` (strict keys; ownerId is rejected on patch). The text fields are NFC, trimmed and non-empty, with limits of name 120, type 60 and inventoryNumber 60. The UI can reuse these directly, because `ui` may import `lib`.
- Error codes `device_placed`, `inventory_number_taken` and `mac_taken` already exist in `src/lib/api/error.ts` and in `src/ui/copy/api.ts` (lines 40-42). `member_not_assignable` currently reads "This member can't be assigned to a seat." (api.ts:25). The server (devices.ts:325) returns it for a create with an inactive owner, so that text is wrong for devices.
- `createDevice` also returns 422 `no_linked_member` and 422 `not_allowed` (a non-Admin passing someone else's ownerId), and 404 for an unknown owner.
- The rooms template is `RoomsPage` (a `Dialog` union, `useMemo` api, `useSession`), `RoomsView` (pure), and `useRooms` (guards). `RoomFormDialog` uses an outer null wrapper, an inner component keyed by id, `EntityFormDialog` and `DialogField`. `rooms-api.ts` has `call`, `errorCode` and `fail`, which are not shared.
- `DeleteRoomDialog` loads the impact, shows one step, and re-checks after a 409. The Devices delete flow is driven by the error instead.
- The member picker lives in `src/ui/seats/`: `MemberPickerFields` (props only), `useMemberPicker(loadPage, reloadToken)`, `member-picker.ts` (reducer, `PickerMember`, `LoadPage`), and `seatsApi.activeMembers(q, cursor)`. The copy is `seatsCopy.actions.picker*`. It is wired to a `SeatDto` only in `MemberPickerDialog`; `MemberPickerFields` is generic, but its `occupantId` prop disables the "(sits here)" row, so pass null.

## Recommendations
Files, all new under `src/ui/devices/` unless noted:
- `src/app/(app)/devices/page.tsx` returns `<DevicesPage/>`, exported through `@/ui`. The title stays `shellCopy.pages.devices`.
- `DevicesPage.tsx` is the container. It builds `createDevicesApi(apiFetch)` and reads the session tier. The Admin flag only decides whether the owner picker shows. Row actions use the dto's `canEdit`, never the tier. State is `filter: PlacementFilter` and `dialog: none | form{device|null} | delete{device}`. Everyone may create (a device starts in inventory), so "New device" is always shown.
- `DevicesView.tsx` and `DeviceTable` are pure, with props `status, errorCode, devices, truncated, filter, onFilter, onNew, onEdit, onDelete, onRetry`. The table is native, with the columns name, type, inventory no., MAC (`—` if null), owner and placement. Placement text comes from a pure `placementText(p)`: `seatCode · roomCode` ("At seat A-01 (R1)") or "In inventory"; a primary or secondary tag is optional. Edit and Delete buttons render only if `d.canEdit`. Do not render place, move or return controls (SIM-013.3). The filter is three `aria-pressed` segmented buttons, or `DialogSelect` as in audit.
- Filter state: apply it on the server. `devices-api.list(filter)` sends `?placement=`, and `useDevices(api, filter)` reloads when the filter changes, with a counter guard so a stale answer for an old filter is dropped. This keeps `truncated` correct per filter. The alternative is to load "all" once and filter client-side with `filterDevices`, which is simpler but gives wrong counts when truncated. Server-side filtering is the better choice. Keep `devices-state.ts` with `FILTERS`, `emptyText(filter)` and `placementText`. Keep the filter in component state; it is not needed in the URL.
- Show a `truncated` notice, with copy such as "Showing the first 1000 devices".
- `devices-api.ts` copies the rooms `call`/`errorCode` pattern (R4: note the extraction as a follow-up). Methods: `list(filter)`, `create(DeviceCreateValue)`, `update(id, DevicePatchValue)`, `remove(id)`, and `moveToInventory(id, expectedSeatId)` (PUT `/api/devices/:id/placement` with `{seatId:null, expectedSeatId}`; the validator requires `expectedSeatId` to be present). Add `activeMembers` for the picker, either by reusing `createSeatsApi(...).activeMembers` or by a local copy. Preferably construct `createSeatsApi` and pass its `activeMembers` as `loadPage`. That crosses ui/seats → ui/devices, which the layers allow. Importing `MemberPickerFields` and `useMemberPicker` from `../seats/...` is also allowed, but `MemberPickerFields` imports `CLIP` from `SeatsView` and `seatsCopy`. Prefer a small owner field in `device-form` that embeds `MemberPickerFields` and pass its copy untouched; do not move files in this ticket.
- `device-form.ts` is pure and does the real work:
  - `DeviceForm = {name,type,inventoryNumber,mac,ownerId}` (strings, ownerId null), `emptyForm`, `formFromDevice`.
  - `toCreateBody(form, {isAdmin})` and `toPatchBody(form, device)` return `{kind:"ok",body}|{kind:"invalid",field,message}|{kind:"unchanged"}`.
  - They should call `validateDeviceCreate` / `validateDevicePatch` from `@/lib/validate/device`, which keeps a single source of truth. Map `field` to the copy for that field. Do not reimplement MAC regexes.
  - The MAC is normalised through the lib normaliser. Blank means null. On edit, compare the normalised form against `device.mac`, and send `mac` only if it differs, so `AA-BB-…` for the same address is "unchanged". Send null to clear it.
  - Create sends `ownerId` only when the viewer is Admin and picked one. Otherwise omit it (the server uses the caller). A non-Admin must never send ownerId, because the server returns `not_allowed`.
  - Optionally add a live `macHint` on blur that rewrites the field to the normalised value.
- `DeviceFormDialog.tsx` follows `RoomFormDialog`: an outer wrapper, an inner component keyed by `device?.id ?? "new"`, `EntityFormDialog` and `DialogField`. Type is a text input with `list="device-types"` and a `<datalist>` filled from `devicesCopy.typeSuggestions` (PC, Laptop, Monitor, IP phone, Other; D37), with maxLength from `DEVICE_LIMITS`. On edit, the owner is shown read-only (`owner.displayName`, disabled field or text). On create the owner picker shows for Admin only, defaulting to "Me" (null owner). On submit, `not_found` on edit means the device was deleted, so call `onDone` (as in rooms). On create, `not_found` means the picked owner was removed, so show an error and don't close.
- `DeleteDeviceDialog.tsx` is driven by 409 `device_placed`, per D31:
  - The first submit calls `api.remove(id)` directly.
  - A pure `delete-flow.ts` holds `type Step = "confirm" | "placed"` and `nextStep(step, code)`. A `device_placed` response moves to `placed`, and the dialog shows the "Move to inventory" action with explanatory copy that names the seat.
  - Do not branch on `device.placement` up front; the server is the authority, and the list may be stale.
  - "Move to inventory" calls `moveToInventory(id, expectedSeatId)`. Take `expectedSeatId` from the row's placement. On 409 or 422 for a changed seat (check the code the placement route uses for `expectedSeatId` mismatch, probably the same one as for stale), reload and show the message. On success, either return to `confirm` or retry `remove` automatically. Prefer returning to `confirm` with the button "Delete device", so each step is an explicit user action; the ticket says "offers Move to inventory and then the delete".
  - `not_found` on either call means done.
  - Moving to inventory by a non-owner Manager is `canPlace`, not `canEdit`. Since delete is shown only when `canEdit` (owner or Admin, who are also allowed to place), that holds. Verify in the server code that Admin and owner both pass `canPlace`.
- Error copy (`src/ui/copy/api.ts` is the only place with codes): do not edit the shared `member_not_assignable` text. Add a device-specific mapping in `devicesCopy.errors` that is applied before `apiErrorMessage`: `deviceErrorMessage(code)` returns, for `member_not_assignable`, "This member is inactive, so they can't own a device."; for `no_linked_member`, a "Your account has no member profile yet" style line; and otherwise `apiErrorMessage(code)`. Also have `inventory_number_taken` and `mac_taken` (already in api.ts) set a field-level message if cheap. Unit-test `deviceErrorMessage`. The `satisfies Record<ApiErrorCode,string>` in api.ts does not need new keys.
- Copy: `src/ui/copy/devices.ts` holds the title/filters/columns/empty states per filter/dialog titles/field labels/typeSuggestions/delete step texts/errors. No string literals in components (the `no-literals` test). Register it the way the other copy modules are exported (check `src/ui/copy/index` or `copy.test.ts`).
- Testability (Vitest node, `renderToStaticMarkup`):
  - `devices-state.test.ts`: `placementText`, `emptyText` for each filter.
  - `device-form.test.ts`: the MAC forms (`AA-BB-CC-DD-EE-FF`, `aabb.ccdd.eeff`, bare, invalid), blank becomes null, unchanged when the same MAC in another format, patch only changed keys, a non-Admin create omits ownerId, and invalid maps to the right field.
  - `devices-api.test.ts`: fake fetcher, URL and method per call, a 409 `device_placed` becomes `{ok:false,code}`, `ApiAccessError` and network failure.
  - `delete-flow.test.ts`: the `confirm` → `placed` → `confirm` transitions.
  - `DevicesView.test.tsx`: the table shows placement for placed and inventory; Edit/Delete are present only when `canEdit` is true (include a row with false); the three filters mark the active one; the loading, error, empty-per-filter and truncated states.
  - A static render of `DeviceFormDialog` inner is not needed; test `DeviceFormFields` as a props-only component if the datalist and read-only owner need coverage. Split fields into a props-only component, like `MemberPickerFields`, so the Admin-only owner picker and read-only owner can be asserted in a static render.

## Risks
- Stale `canEdit`: a role change makes the server answer 403/422 `not_allowed`; show it with `apiErrorMessage` and reload.
- Filter race: switching filters quickly returns out-of-order responses; the guard counter is required.
- The delete-then-move flow uses `expectedSeatId`; if another user moved the device in between, the move returns a stale-placement error. Handle it by reloading the list and closing the dialog with a message, not by silently deleting.
- Reusing `MemberPickerFields` brings `seatsCopy` strings ("Search members" etc. are generic) but also `CLIP` from `SeatsView`; coupling is acceptable for now but should be a follow-up to move the picker to a shared folder.
- The 1000-device cap with no paging; show the `truncated` notice, and note paging as a follow-up.
- R7 holds on the server; the UI must not rely on `apiFetch`'s re-send for writes, since it re-sends once on 401/403.
