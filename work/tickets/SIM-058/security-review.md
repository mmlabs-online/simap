# Security review — SIM-058

## Attempt 1

**Summary: PASS from security. No blockers and nothing should-fix. Org scoping (R6), R7, ownership, privacy, audit and the migration all hold up on reading the code; three notes below.**

Scope read: `db/migrations/20261126150000_presence.sql`, section 14 of `scripts/schema-check.mjs`, `src/server/presence/{sql,presence,read,end}.ts`, `src/lib/validate/presence.ts`, `src/lib/api/error.ts`, both new routes, and the D82 call sites in `seats.ts` (lines 330-339, 522), `manage.ts:424` and `rooms.ts:252`. I could not run commands in this review, so check results (`pnpm test`, `pnpm test:db`, `schema:check`) have to come from the implement log or CI.

### What I checked
- **R6 org scope.** Every presence, seat, room and member query, every update and every audit insert goes through `orgQuery`. `orgQuery` (`src/server/http/org-scope.ts:21-24`) requires `org_id = $1` and always binds `scope.orgId` itself, so the caller cannot choose the org. Every join repeats `org_id` (`sql.ts:5-7`, `read.ts:34`). The member and seat FKs are composite `(org_id, …)` (migration lines 22-23), and schema-check proves both cross-org cases are refused with 23503 (lines 1257-1262). Another org's room gives 404 on check-in (`presence.ts:117-123`) and on read (`read.ts:20-26`). Another org's seat on move is not found by the org-scoped lookup, so it gets 422 `seat_not_yours`, which also avoids an existence oracle.
- **R7.** `Refusal.status` is typed `404 | 409 | 422` (`presence.ts:15`) and the room read can only return 404. The routes themselves return only 400 and 503, so no 401/403 comes from outside `withAuth`. Every refusal is thrown as `Abort` inside `withTx`, which rolls back, and each refusal check (lines 82-84, 123, 144-147, 242, 248, 255) runs before the first write. A late refusal cannot leave a write behind.
- **Acting for another member / foreign seat.** The member is always resolved from `ctx.sub`, the verified token (`lockOwnMember`, `presence.ts:75-87`). No route accepts a member id. Check-in takes only a seat whose `occupant_id` is the caller, in that room (lines 124-130). Move locks both seats `for share` and re-checks that the old seat is still held and the target's occupant is the caller (lines 246-255, `decideMove`).
- **Client cannot supply times.** The validator accepts exactly one uuid key and refuses any extra key (`validate/presence.ts:9-10`). `now` is not a route input: the route calls pass no `now` (`route.ts:31,54,65`). `work_date` and `checked_in_at` come from one server clock read.
- **Room read privacy (SIM-050/052).** It returns only `memberId, displayName, seatId, seatCode, checkedInAt, source` (`read.ts:31-32, 44-51`). There is no email, sub, group, photo, device or `checked_out_by`. Only active rows are listed: today, open, seat still held (`activeWhere`), and `m.status = 'active'`. No presence references in `src/server/export/**` or `src/server/dashboard/**` (D78).
- **Audit.** Self actions use `actorSub: sub` from the token. D82 system check-outs use the acting admin's sub, as planned, because `actor_sub` is `uuid not null`. Meta holds room and seat codes, a member uuid, a reason and a boolean. Nothing sensitive.
- **Migration.** It adds one new table and one index, nothing else: forward-only and expand-only. No `begin`, grant or `concurrently`. The constraints are named, and the index starts with `org_id`. The schema-check section 14 cases run in transactions that roll back (`tx(..., false)` or a refused insert), so they leave no rows behind.
- **Secrets / R3.** No secrets, env access or logging were added.

### Findings
- 💭 `src/server/presence/end.ts:45`: the `presence.system_check_out` meta stores `seat: r.seat_id` (a uuid). The other presence audits store seat and room codes (`presence.ts:175, 214, 274`). After a forced `deleteRoom` the cascade deletes the seat, so this uuid can no longer be resolved and the audit trail loses which seat it was. No security impact. Fix (optional): add `returning … (select code from seats x where x.org_id = p.org_id and x.id = p.seat_id) as seat_code` and log the code. That changes the audit meta shape, so it needs the orchestrator or Ming to agree.
- 💭 `src/server/presence/presence.ts:194-216`: `checkOut` also closes a today row that is open but whose seat the member no longer holds (a "stale" row from the previous image or a raw write). It audits that as `presence.check_out` by the user. The plan accepts this ("closed too, without a separate code path") and it is harmless. Noted only because the audit can show a self check-out of a row the user never saw as active.
- 💭 `src/server/presence/presence.ts:160-167`: the plan's `on conflict (org_id, member_id, work_date) do nothing` plus re-read is not in the insert. Today the member-row `for no key update` lock serialises a member's check-ins, so the unique key cannot fire (the plan's `Promise.all` DB test covers this). If a future writer inserts presence without taking the member lock, a duplicate would surface as a 500, not a security hole. Fix (optional): add `on conflict on constraint presence_org_member_date_key do nothing` and handle an empty `returning` by re-reading.
