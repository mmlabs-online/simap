# Consult — ux-architect (SIM-014.3)

## Findings

**Backend (SIM-014, already merged) gives everything the UI needs**
- `POST /api/requests {seatId}` returns **201 when created and 200 when a pending duplicate already exists** (body is the RequestDto in both cases). Refusals: 409 `seat_taken`, 409 `seat_cannot_seat`, 422 `no_linked_member`, 422 `member_not_assignable`, 404 `not_found`. Tier `user`.
- `GET /api/requests/mine` returns `{items: MyRequestDto[] (isNew), unseen, nextCursor}`. `POST /api/requests/mine/seen` takes `{seenUpTo}` and returns `{unseen, requestsSeenAt}`. The mark moves forward only and is capped at now. `POST /api/requests/[id]/cancel` exists.
- "New" means status approved or rejected with `decided_at` later than `members.requests_seen_at`. Cancelled requests never count. The count is server-side, so the badge is the `unseen` number and the client does no counting.
- Duplicate detection cannot rely on an error code. The existing `seats-api.ts` and `requests-api.ts` collapse responses to `{ok, code}`, and `requests-api.ts` only has a GET `call`. The new create call must keep the HTTP status (201 vs 200) and return something like `{ok:true, created:boolean}`. Note that `actionOutcome` is documented as "from `result.code` only (never the HTTP status)". The duplicate is therefore best expressed as a distinct pure outcome, not a status check inside `actionOutcome`.

**Existing patterns to follow**
- `src/ui/seats/seat-actions.ts`: `seatButtons(tier, seat)` returns a flat boolean record. Add `request: boolean`. `SeatActions.tsx` has a hard-coded "any button" OR-chain that must also include `buttons.request`, otherwise a User with only that button gets no row. `SeatAction` union and `actionOutcome` have a final fall-through branch that treats unknown actions as release (`not_allowed` becomes `releaseChanged`). A new `"request"` action must get its own branch before that fall-through.
- Button rule: `request = tier === "user" && !seat.occupant && !seat.cannotSeat`. The ticket says Users only, while Managers and Admins assign directly (REG-02, SEA-03). Use an exact-tier check, not `atLeastTier`. The server also allows managers, so the hiding is UX only. `seat.mine` implies an occupant, so it is already excluded.
- `ApprovalsView` (pure view with a `state` of loading, error, ready or forbidden, a Card per row, a Chip for status, `formatRequestTime`, `requestsCopy.statusLabel`) is the template for `MyRequestsView`. Reuse `statusLabel`, `seatLine`, `requestedAt`, `decidedLine`, `emptyFor`, `retry`, `loadMore` from `src/ui/copy/requests.ts`. The Approvals page shows no Chip for pending rows and shows `decidedLine` for decided ones.
- `AppShellView` renders nav items from `navItemsFor(tier)` filtered to `placement === "rail"`. Each is a `Link` with an icon in a `w-14 h-8` pill plus an 11px label. `shellCopy.nav[item.id]` and `shellCopy.pages.*.title` are keyed by `NavId`, so adding `myRequests` needs entries in both. `nav.ts` has `NavId` and `NAV_ITEMS` (add `{id:"myRequests", href:"/requests", icon: <existing IconName>, minTier:"user", placement:"rail"}`). Check `src/lib/icons.ts` for a suitable icon name (e.g. `fact_check` is taken by Approvals; pick another, such as `inbox`, `assignment` or `event_seat`, only if it is in the icon set).
- `isActive` uses `startsWith(href + "/")`, so `/requests` does not collide with `/approvals`.

## Recommendations

1. **Request button (AC1).** Place it in the seat panel `SeatActions` row as `variant="tonal"` (or primary, since it is the main User action). Label "Request this seat". Show it only per the rule above. Disable it while `busy`. Add `seatsCopy.actions.request`, `requestDone` and `requestDuplicate`. A cannot-seat seat shows no button. Optionally show a one-line hint ("This seat is not available for assignment") using the existing cannot-seat reason UI, since D26 says the flag blocks requests.
2. **Feedback.** The panel's `notice` is `role="alert"` red text only (`text-error`), which suits errors but not success. For success, add a separate `role="status"` line in the panel (neutral or primary colour):
   - 201: "Request sent. A manager will review it."
   - 200: "You already requested this seat." (informational, not an error).
   - After success, either leave the button enabled (the server dedupes) or, better, replace it with a disabled state or a note "Requested" for the rest of the panel's life. Without a "my pending requests" lookup the panel cannot know on reopen, so keep this local and cheap: the duplicate response is the source of truth, and it is idempotent and harmless.
   - Do not reload the seat list on success (the seat is unchanged). Reload on `seat_taken`, `seat_cannot_seat` and `not_found` so the panel shows the real state. Messages: `seat_taken` gives "Someone else was seated here. Pick another seat.", `seat_cannot_seat` is unavailable, `no_linked_member` and `member_not_assignable` fall back to `apiErrorMessage` (check `copy/api.ts` has entries for all of them, including `seat_taken` and `seat_cannot_seat`).
3. **My requests page `/requests`.**
   - Title via `shellCopy.pages.myRequests.title` ("My requests").
   - Vertical list of Cards (no table), one per row: seat line, status Chip (show it for all statuses, including Pending, unlike Approvals, because the status is the point of this page), requested time, and for decided rows `decidedLine` (e.g. "Approved by X on …"). Mark `isNew` rows with a small "New" Chip, and keep it visible during this visit even after the seen call (snapshot `isNew` at load time, so the user sees what changed).
   - No filter chips (the list is the user's own and small). Use a Load more button for `nextCursor` (same pattern as Approvals).
   - Cancel: only on pending rows, a `variant="tonal" size="sm"` button inside the Card. Recommend **no confirm dialog**: it is cheap and low-risk, the user can simply re-request, and the Approvals slice used a decision dialog only for heavy actions. Compensate with the busy or disabled state during the call, and after success update the row in place to "Cancelled" and announce it via an `aria-live="polite"` line. If Ming prefers a confirm, reuse the `ConfirmSeatDialog` pattern; list this under the open questions. Cancel errors: a 409/422 (the request was decided in the meantime) should reload the list and show "This request was already decided." Handle `not_found`.
   - Empty state: a Card with "You have no seat requests yet." and a `Link` button to `/rooms` ("Browse rooms").
   - Narrow screens: single column Cards with `min-w-0 break-words`, wrapped flex rows (`flex-wrap`), the Cancel button full row below on narrow widths. No horizontal scroll. Tap targets `min-h-11`.
   - A User with no linked member gets an empty list from the API (`unseen: 0`), so the empty state is shown. This is acceptable, optionally with a note.
4. **Badge (AC3).**
   - Add an optional `badges?: Partial<Record<NavId, number>>` prop to `AppShellView` (default `{}`), keeping the view pure. A new `useRequestBadge` hook (fetch `/api/requests/mine?limit=1` or a lighter read, on mount, on pathname change, on window focus and visibilitychange; no polling per D24) feeds it from the `AppShell` wrapper. Fetching `mine` with `limit=1` is enough to read `unseen`, with no extra endpoint needed. Skip fetching when there is no session. On failure keep the last known count (never show an error in the nav).
   - Placement: a small circular count on the top-right of the icon pill (inside the `w-14 h-8` span, `relative`, badge `absolute -top-1 right-1`), same on rail and bottom bar. Cap the display at "9+". Hide at 0.
   - Accessibility: the Link's accessible name must include the count. Add a visually hidden text next to the label, e.g. `shellCopy.badge.requests(n)` = "N new decisions" (sr-only inside the Link), and mark the visible numeral `aria-hidden`. Do not use `aria-live` on the nav (it would announce on every route change). The badge must not rely on colour alone (it has a number). Check contrast of the badge colours against `--accent-*` / `error` tokens in light and dark themes.
   - Clearing: on opening `/requests` (page mounts and the list loads OK), call `POST /api/requests/mine/seen` with `seenUpTo` = the newest `decidedAt` among the loaded items, or null (server uses now). Prefer passing null only if the first page was fully loaded. Using the max `decidedAt` of the fetched page is safer: a request decided between the list fetch and the seen call would otherwise be silently marked seen without the user seeing it. Then set the badge from the response's `unseen` (this needs a shared state or event between the page and the badge hook, such as a small context or a custom window event; keep it pure-testable, e.g. a `badge-state.ts` with `nextBadge(prev, event)`). Mark seen only on success of the list load, not on error. The server value is the source of truth, so a refetch on the next route change corrects any drift.
   - The badge should also appear for Managers and Admins (they also hold a member row). `myRequests` is minTier `user`, so it shows for all tiers.
5. **Rail capacity.** The rail is a `flex justify-around` bottom bar on mobile. Admins would have 7 entries (dashboard, rooms, devices, members, approvals, audit, myRequests). At 320 to 360 px width each `w-14` pill (56 px) times 7 is about 392 px, so it will overflow or squash. Verify and either shrink the pill on small screens (`w-12`), allow the bar to scroll horizontally, or place My requests only for tiers where it matters (but Managers and Admins can still hold requests). Flag this in the plan as a layout check at 360 px.
6. **Tests (AC4, no jsdom).** Pure logic: `seatButtons` request rule for user, manager, admin, occupied, cannot-seat, mine; `actionOutcome("request", ...)` branches; duplicate vs created mapping; badge reducer (0, cap at 9+, keeps last on failure, clears on seen response); `seenUpTo` selection (max `decidedAt`); sort and `isNew`. Static render (`renderToStaticMarkup`) for `MyRequestsView` (loading, error, empty, ready with pending and decided and isNew, cancel button only on pending), `SeatActions` with the Request button, `AppShellView` with and without `badges` (sr-only text, `9+`, hidden at 0). Also extend `no-literals.test.ts` expectations by keeping all strings in `src/ui/copy/requests.ts` and `shell.ts`.

## Risks
- `actionOutcome` falls through to release for unknown actions. Without a dedicated branch, request errors show the wrong text.
- `apiFetch` re-sends once on 401/403 (R7). Create and cancel are idempotent (duplicate returns 200, cancel of a non-pending request is a no-op or 409), so a repeat is safe. Still do not add any side effects before the auth wrapper.
- Marking seen too early (before the user sees the list) or on a failed load would silently drop the badge. Mark only after a successful load, with `seenUpTo` = the newest loaded `decidedAt`.
- A stale "Request this seat" button after another user takes the seat yields `seat_taken` (409), which the UI must handle with a reload.
- Badge fetch on every route change and focus adds load. It is cheap (`limit=1`), but avoid running it while signed out or during the loading state, and debounce focus events.
- Bottom bar overflow with 7 items on narrow screens (see recommendation 5).
- The spec's REG-01 says "any signed-in user with a linked member". A User without a linked member gets 422 `no_linked_member` on click. Consider hiding the button when the session has no linked member, if the session exposes it. Otherwise handle the message.

## Open questions
1. Cancel with or without a confirm? Recommended: no confirm (low risk, re-requestable). Needs Ming's choice.
2. Should Managers and Admins see "Request this seat"? The ticket says Users only (they assign directly). Recommended: exact tier `user`.
3. Which icon for `myRequests` (check availability in `src/lib/icons.ts`)? Label text: "My requests" (the D24 Vietnamese name "Yêu cầu của tôi" is not used because UI copy is English, D36).
4. After a successful request, should the panel remember it (disabled "Requested") or stay re-clickable? Recommended: local disabled state for the open panel, with the duplicate 200 as backstop.
5. Should the "New" Chip stay on rows after the seen call during the same visit? Recommended: yes (snapshot at load).
6. Should `/requests` also be reachable from the seat panel feedback ("View my requests" link after success)? Optional nicety, small cost.
