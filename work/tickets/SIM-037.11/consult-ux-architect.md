## Findings

Existing patterns (all in src/ui/devices unless noted):
- Page composition: `DevicesPage.tsx` owns state. It passes an `incoming` ReactNode (IncomingTransfers + PendingReturns) to `DevicesView`, rendered between the notice and the filter chips. `DevicesView` is pure.
- `PendingReturns.tsx` is the template for the extensions list. It is a section with an h2 (`headingRef`, tabIndex -1), hint, error+retry, a Card per item, `canConfirm`/`canCancel` buttons with aria labels, and `data-handoff-confirm` for focus. It renders nothing when empty and has no error.
- `act(list, item, call, outcomeOf)` in DevicesPage does the work. It uses a single `acting` ref lock, `refreshAll()` (incoming, returns, device list and count), and `focusAfter`. `useHandoffList(api, box, enabled)` and `handoffBoxes(isAdmin)` gate the box. `box=extensions` is Manager+, so a non-Manager must never request it (it answers 422).
- `incoming-transfer.ts`:
  - `badgeCountAfter` already returns `extensions:0, overdue:0` in its fallback.
  - `badgeTotal` is still `incoming + returns`.
  - `handoffActionFailed` is shared by all kinds.
  - `FocusTarget.section.list` is a `HandoffBox`, but DevicesPage maps only returns vs incoming to a heading ref.
- `AppShell.tsx` passes `badgeTotal(handoffs)` and `shellCopy.badge.devicesBreakdown(incoming, returns)`. That function (copy/shell.ts l.8-13) is a two-part special case. A four-part list needs a rewrite.
- Row chips: `OwnerLabel` in `DeviceTable.tsx` shows the owner, a "You" chip, `pendingText` chip, "to" line, and the expiry/note lines. `pendingText` ignores extensions today (devices-state.ts l.33-42). `rowActions` (`device-actions.ts`) lists cancel only for transfer/return, so extension cancel is excluded.
- Filters: `FILTERS` in devices-state.ts is missing `overdue`. `devicesCopy.filters`/`empty` are `Record<PlacementFilter,...>`, so typecheck will fail until the key is added.
- Dialogs: `ReturnDeviceDialog` plus `EntityFormDialog` and `NoteField` is the dialog template. `AssignDeviceDialog` has a date input with `expiryMin(mode, holding, today)` and `focusDate`. Check `assign-device.ts` for a reusable today/min helper. `todayUtc7` is in `src/lib/devices/holding.ts` and is lib-pure, so the UI can import it.
- API/DTO (SIM-037.5, merged):
  - `DeviceDto.overdue` is only true when the device is owned and the expiry is before today.
  - There is no `canExtend` flag.
  - `PendingHandoffDto` has `newExpiresOn` and `canCancel`.
  - `HandoffDto` has `newExpiresOn`, `device.expiresOn`, `canConfirm`, `canDecline` and `canCancel`.
  - Extension confirm is Manager+. Extension decline is Manager+ via `POST /api/handoffs/:id/decline` (check that `devices-api.ts` has it).

## Recommendations

Flow and layout (AC 1-4):
1. **Overdue filter (AC1).** Add `"overdue"` to `FILTERS` (last position). Add `filters.overdue = "Overdue"` and `empty.overdue = "No overdue devices."`, and keep `summary` working. Keep the filter visible to everyone: the server scopes `overdue` as the device's overdue flag org-wide, not owner-only. The Overdue chip on rows uses `d.overdue` only, so a no-expiry device can never get it. Place it in `OwnerLabel` beside the You and pending chips, with a danger tone if `Chip` supports one (else add a `tone` prop). It must not rely on colour alone, so keep the text "Overdue", and put the expired date in the expiry line ("Expired 2026-11-24" in place of "Until ..." when overdue).
2. **Pending extension chip.** Extend `pendingText` to `kind==="extension"` with chip "Extension pending" and a second line "New date 2026-12-31" from `p.newExpiresOn`. This replaces the "until SIM-037.5" doc comment.
3. **Owner banner.** Put it in `DevicesView` as a new `banner` slot above `incoming`, or inside the `incoming` node (cheapest, no view change). Show it only when the caller has at least one `d.mine && d.overdue` device. Source this from the count (`overdue`), not the filtered list. The list may be filtered, so the banner would otherwise vanish when the user switches to another filter. Plan: a small `useOverdueDevices` fetch of `placement=overdue&mine` is not available, so use the count for the heading ("2 of your devices are overdue") and fetch `?placement=overdue` separately in the page (filter by `mine` client-side). Show up to 5 devices, each with name, inventory number, expired date, and the buttons Extend and Return. A device with a pending handoff shows its pending chip instead of the buttons, plus Cancel for an extension, so a pending extension does not offer a second Extend. Use `role="region"` with an `aria-labelledby` h2 (not `role=alert`, to avoid noise). It is not dismissible, because overdue is computed and the reminder is by design persistent. Place it above the incoming transfers, because it is the most actionable item.
4. **Row actions.** Add `onExtend` and `canExtend` (derive it client-side as `d.mine && d.overdue && !d.pendingHandoff`, or from a Manager's direct expiry edit via the existing `editHolding`). Should Extend also show for a not-yet-overdue owned device? Spec says the owner requests when overdue; keep it to overdue only for v1. Add cancel for the extension in `rowActions` (`cancelExtension`, label "Cancel extension", aria with inventory number). `onCancelHandoff` in the page must pass `"extension"`, since `cancelOutcome` currently takes `"return" | "transfer"`; extend that type and its copy.
5. **Extend dialog.** New `ExtendDeviceDialog` mirroring `ReturnDeviceDialog` (keyed by device, mounted only when open). Fields: read-only current expiry, a date input (label "New expiry date") with `min` = tomorrow (UTC+7, from `todayUtc7` plus 1 day, so it lines up with `day > today`), and `NoteField` (optional). Logic goes in `extend-device.ts` (`emptyExtendForm`, `toExtendBody` returning an invalid message on a missing date or `<= today`, `settleExtend`), with unit tests. Handle `handoff_pending`, `device_unowned` and `not_allowed` via `apiErrorMessage` and `onStale` to refresh. On success the notice reads "Extension requested for NAME (INV). Waiting for a manager to approve." and focus goes back to the page heading, like the return flow.
6. **Pending extensions (Manager+).** Add `PendingExtensions.tsx`, a clone of `PendingReturns` with the heading "Extension requests (n)" and item lines: device, "Owner: X", "Expires 2026-11-20, requested new date 2026-12-31", and the note. Buttons: Approve (`canConfirm`) and Reject (`canDecline`). Do not label them Confirm and Cancel. In the page, use `useHandoffList(api, "extensions", isManager)`. Outcomes: add `approveExtensionOutcome` ("Extension approved: NAME now expires on DATE") and `rejectExtensionOutcome`. Put it after PendingReturns. If PendingReturns and the new list share enough markup, extract a shared `HandoffSection` to avoid a third copy (but keep it inside this ticket's size; a straight clone is acceptable and lower risk). Extend `act` and `focusAfter` to handle `list === "extensions"` (third heading ref). Note `focusAfter` uses `canConfirm` for next-item focus, which suits Approve.
7. **Badge.** Define `badgeTotal = incoming + returns + extensions + overdue`. Change `devicesBreakdown(c: HandoffCountDto)` to take the count object and produce the parts, zero parts omitted: "3 pending items: 1 incoming transfer, 1 pending return, 1 extension request, 1 overdue device". Keep the existing single-part strings unchanged for compatibility with `AppShellView.test.tsx`. `byNav.devices` in shell copy stays as the fallback. Update `ZERO` in `useHandoffBadge.tsx` and the `devices-api` count parser to read `extensions` and `overdue` (default 0 when missing, for an older server during rollout).
8. **Refresh.** `refreshAll` must refresh the extensions list as well, and the overdue device list, then compute the badge with `badgeCountAfter(count, inc, ret, ext)`. The fallback should use list lengths for extensions, and keep the previous `overdue`.
9. **Copy (AC4).** All new strings in `src/ui/copy/devices.ts` (a `devicesCopy.overdue`, `.extend`, `.extensions` group) and `shell.ts` for the badge text.
10. **Seed.** Add a device in the dev seed owned by the dev user with `holding_expires_on = today UTC+7 minus 1 day`, one owned by another user also overdue (to check the Manager view), and one pending extension. Keep it local-DB only, as with the rest of `seed:dev`.
11. **Tests.** Unit: `pendingText` extension, `filterOptions`, `badgeTotal`/`badgeCountAfter`, `devicesBreakdown`, `toExtendBody` (date <= today invalid), `settleExtend`, extension outcomes, `rowActions` (extend and cancel only for overdue owners with no pending handoff), api client paths (POST `/api/devices/:id/handoffs` with `{kind:"extension"}`, `GET /api/handoffs?box=extensions`). Markup: banner, ExtendDialog, PendingExtensions, Overdue chip, `DevicesView.test.tsx` updates.

## Risks
- Hiding the banner when the list is filtered (see 3). Drive it from the count and a separate overdue fetch, not from `items`.
- `box=extensions` for a non-Manager returns 422. Gate the hook by tier (`atLeastTier(session.tier, "manager")`), as `handoffBoxes` does for admin.
- `Record<PlacementFilter,...>` copy and `FILTERS` give compile errors until all keys are added (good guard, but touches several tests).
- Date handling: never use `Date` for display (the existing `expiryText` rule). The date input min must use the UTC+7 day (`todayUtc7`), otherwise a user near midnight sees a mismatch with the server's `day > today` check. A `handoff_stale` or validation 400 on `newExpiresOn` needs a field-level message.
- Concurrency: the `acting` lock and `busyId` are shared; the extension actions must go through the same lock, or two clicks can double-submit. R7: 401/403 are re-sent once by `apiFetch`, which is safe here because the server checks permission before writing.
- `cancelOutcome` and `cancelHandoff` currently assume return/transfer wording; reusing them for extensions without a kind argument gives wrong notice text.
- Badge total now counts an owner's overdue devices, so the badge never clears until the owner acts (intended per spec, but worth stating to Ming). An owner with many overdue devices could show a large badge (`overflow` "9+" exists).
- Size: M may stretch to L. If so, split the banner and Extend dialog (owner side) from PendingExtensions (Manager side).

## Open questions
1. Should the Extend action also be offered to a Manager+ for someone else's overdue device? The spec says Manager+ edits the expiry directly (`editHolding`), so I recommend no.
2. Should Extend appear before the expiry passes (due soon)? Ticket says no, due-soon is out of scope. I assumed overdue only.
3. Should the banner list devices (max 5) or only a count with a link to the Overdue filter? I recommend a short list with buttons, since the ticket requires Extend and Return actions in the banner. A count-only banner with "Show overdue" is cheaper if Ming prefers it.
4. Does the badge for a Manager who is also an owner double count? The API returns separate fields, so the sum is simple; confirm this is acceptable.
5. Does `devices-api.ts` already have `declineHandoff` that works for extensions (reject)? It is used for transfers, so it likely does, but verify the route accepts kind extension.
