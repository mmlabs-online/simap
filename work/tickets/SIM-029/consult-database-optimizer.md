# Consult — database-optimizer (SIM-029)

## Findings

Current state:
- **Existing guard.** `assertDevSeedTarget` (db/seeder.js) is the only guard. It does three things: it refuses NODE_ENV=production, it refuses a URL whose query string has `host` or `hostaddr`, and it requires the host from `pg-connection-string` `parse()` to be in {localhost, 127.0.0.1, ::1, [::1]}. A tunnel URL on 127.0.0.1:15432 passes it today, so that is the gap.
- **Which scripts have a guard:**
  - Guarded: `seed-dev.js`, `test-db.mjs`, `schema-check.mjs`, and `src/test/db/global-setup.ts`. The last one is a second entry into vitest.db.config, so a direct `vitest -c vitest.db.config.ts` run bypasses test-db.mjs. The shared guard covers it.
  - Not guarded: `db/migrate.js` and `scripts/migrate-smoke.mjs`. Both read DATABASE_URL and connect with no check. `migrate.js` only checks that DATABASE_URL is set. `migrate-smoke.mjs` runs `create database` on whatever DATABASE_URL points at.
- **`--env-file-if-exists=.env.local`.** The package scripts for migrate, migrate:smoke, test:db, schema:check and seed:dev all load `.env.local`. A prod URL there would be picked up silently, but dev:prod refuses that case. Node's `--env-file` does not override variables already in the environment, so the dev:prod child env wins.
- **Container path.** The Dockerfile copies only `db/migrate.js` and `db/migrator.js` into `./db/`. `db/seeder.js` is not copied, and `pg-connection-string` is a devDependency. If migrate.js imports the new classifier from seeder.js, or from anything that imports `pg-connection-string`, the image breaks at startup. The new classifier file must have no dependencies. The Dockerfile would then need to COPY it, which is an edit to a High-path file and needs a Dockerfile change in the plan.
- **No file in the image can be skipped.** `import` is static, so the classifier must be in the image or it must be inlined into migrate.js.
- **How the app uses the URL.** `src/server/db/pool.ts` uses only DATABASE_URL, so dev:prod works by putting DATABASE_URL in the child env.
- **Likely hole in the port-only rule.** Prod `DATABASE_URL` through the tunnel is `127.0.0.1:15432`. Other ways to reach prod stay open. Examples are a different local forward port, the PG* env vars, and `?port=`.

## Recommendations

### 1. Classifier
Create `db/target.js` (or `scripts/`), plain JS with zero imports (so it is image-safe and shared by `.mjs`, `.js` and the TS global-setup). Signature: `classifyTarget({databaseUrl, env}) → {production: boolean}`. Messages never contain the URL.

Rules, in order. Treat the target as production when any of these hold:
1. `env.SIMAP_DB_TARGET` is `production`, compared case-insensitively and trimmed. Any other non-empty value (including a typo like `prod`) should also be refused, or at least `prod`/`production`. Failing closed is safer. Accept only unset, `local` or `dev` as non-production.
2. The URL's effective port equals the tunnel port. Tunnel port = `SIMAP_PROD_TUNNEL_PORT` if it is set and valid, else 15432. If the override is set but not an integer 1-65535, fail closed (treat as production, or exit 2 with a config error). Do not silently fall back to 15432.
3. The URL is unparsable, or the port is unparsable or contains non-digits, or the query has `port`. Treat as production in the migrate-type scripts (refusal is already the behaviour for an invalid URL).

Edge cases to handle in the classifier:
- **Query-string `port`.** pg-connection-string honours `?port=` (and `?host=`, which the existing guard rejects). Reject `port` in the query outright, as the existing code does for `host` and `hostaddr`. Do not try to reconcile the two ports.
- **Multi-host URLs** (`postgres://a:1,b:2/db`). `new URL` rejects them, which gives a refusal. Confirm it does and add a test.
- **IPv6 `[::1]:15432`.** `new URL(...).port` handles this. Test it.
- **Default port.** An empty port means 5432, so it is not production.
- **Port normalisation.** `new URL` strips `:05432`? Parse with Number on the string. Make sure `015432` or `15432.0` are not a bypass. Use `/^\d+$/` and `Number()`, or just trust `new URL().port` (which normalises). Test `postgres://h:015432/` and `postgresql://` scheme variants.
- **sslmode and other query params.** These are not port-bearing and can be ignored. But `sslmode=` on a loopback target is not a prod signal, so do not use it.
- **Unix-socket and `host=/path` forms.** The existing guard refuses them (query `host`, or non-local host). Keep that.
- **PG* env vars.** The client does not read PGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD when a connectionString supplies the value, but they fill gaps. A URL with no port plus `PGPORT=15432` connects to the tunnel. The migrate-type scripts should also check `env.PGPORT` against the tunnel port, and `PGHOST` / `PGHOSTADDR` for non-local values. Simplest and safest rule: in the guarded scripts, refuse when any of PGHOST, PGHOSTADDR, PGPORT is set, or evaluate them as the effective values (URL value wins, else env). Also note that pg may read `PGSERVICE` / `PGSERVICEFILE` (libpq feature; the node `pg` package does not implement it, so low risk, but one line in the plan is fine).
- **Hostname forms of loopback** like `127.1`, `0.0.0.0`, `localhost.` do not need extra handling because the existing LOCAL_HOSTS allowlist already rejects them. Keep an allowlist rather than a denylist.
- **Do not trust host.** The tunnel is on 127.0.0.1, so a host-based rule cannot tell prod from local. This is why port plus the explicit flag is needed.
- **Optional extra signal, cheap.** Also treat a database name or role that is exactly `simap` on a non-5432 port as suspicious? Not recommended: compose.dev.yml uses db `simap`, user `simap` on 5432. Leave it.

Compose a single function `assertDevSeedTarget` (keep the name and call sites) that calls the classifier and throws a message such as `refusing: database target is production`. Add env to its input (`{databaseUrl, nodeEnv, env}`), defaulting to `process.env`. That updates 4 guarded sites at once: seed-dev.js, test-db.mjs, schema-check.mjs, global-setup.ts. Then add the guard to migrate.js (conditionally) and migrate-smoke.mjs.

### 2. Guard placement per script (before any connection)
- **seed-dev.js.** The guard call already precedes `new pg.Client`. Only the shared function changes. Exit 2 stays.
- **test-db.mjs.** The guard precedes `spawnSync`. Good. The child inherits the env, so global-setup re-checks (defence in depth).
- **schema-check.mjs.** The guard precedes `new pg.Client(...).connect()`. Good.
- **migrate-smoke.mjs.** Add the guard right after the DATABASE_URL check and before `dbName`/`admin.connect()`. Use `assertDevSeedTarget` (it also enforces local-only, which this script needs since it creates databases), exit 2, and print a `migrate:smoke refused:` message.
- **migrate.js.** Needs a different rule from the other four (see the container section). Place the check in the `else` branch before `runMigrations`, which is where nothing has connected yet.
- A pure classifier unit test plus one CLI test per entry. Spawn each script with `DATABASE_URL=postgres://u@127.0.0.1:15432/simap`, and again with `SIMAP_DB_TARGET=production` and a URL on 5432. Assert exit 2, empty stdout, stderr without the URL, and no connection. A connection attempt to a dead port would give exit 1, so exit 2 proves the guard ran first. Add CLI tests for global-setup via the vitest config if cheap.
- Make sure test spawns clear `PG*`, `NODE_ENV`, `SIMAP_*` from the child env so the dev machine's env cannot affect them.

### 3. Container migrate path
- The production migrate entry must keep working with a prod DATABASE_URL (any port, any host, NODE_ENV=production in the image). So `migrate.js` should not use `assertDevSeedTarget` (that refuses NODE_ENV=production).
- Proposed rule for migrate.js: refuse (exit 2) only when the process is not the container, i.e. `NODE_ENV !== "production"` and the classifier says production (port 15432 or SIMAP_DB_TARGET=production). Image entry sets NODE_ENV=production? Verify in the Dockerfile and compose/deploy files (I only grepped the migrate lines; read the full Dockerfile and the deployment's `migrate` service env before committing to this). If the migrate service does not set NODE_ENV, the plan must pick another container signal, and anything that can be set by a laptop user (e.g. `NODE_ENV=production pnpm migrate` from a laptop) turns the guard into a bypass.
- **Bypass risk.** `NODE_ENV=production pnpm migrate` on a laptop against the tunnel would then be allowed. That is exactly what the guard must stop. A reliable container discriminator is better than NODE_ENV. Options:
  1. Put the container marker in the image, such as `ENV SIMAP_IN_CONTAINER=1` or `ENV SIMAP_MIGRATE_ALLOW_PROD=1`. A laptop user can set it too, but only on purpose; a deliberate override is not the same as an accident, and it matches the tudocuatui rule "never migrate production from a laptop" as a guardrail against mistakes.
  2. Detect `/.dockerenv` or `process.env.container` (weak and platform-specific).
  3. Make the script wrapper `pnpm migrate` call a separate file (e.g. `scripts/migrate-dev.mjs`) that does the guard and then imports `db/migrate.js`, while the container runs `node db/migrate.js` directly with no guard. Best separation: the pnpm script is the dev surface, the image entry stays untouched, and the Dockerfile and migrate.js need no change. But then `node db/migrate.js` on a laptop is unguarded; a test should state that this is intentional and document it. The ticket says "`pnpm migrate` ... refuse", so this matches the wording exactly.
  Recommend option 3 (guard wrapper for pnpm scripts; the image entry is `node db/migrate.js` unchanged), with the classifier not imported by migrate.js. If ming wants the guard inside migrate.js too, use a classifier file inlined or copied and a Dockerfile COPY line, and an explicit env flag, but this raises the tier and the review cost.
- Test proving the container path is unaffected: spawn `node db/migrate.js` with `NODE_ENV=production`, `DATABASE_URL=postgres://u@127.0.0.1:15432/x` and no DB listening. Assert the exit code is 1 (connect failure) rather than 2 and stderr is not the refusal text. Better, an ESM import check: that migrate.js's static imports are only node: builtins plus ./migrator.js (and ./migrator.js's own imports are in the image). Also a test that the Dockerfile `COPY` list covers every relative import of migrate.js.
- Whatever is chosen, keep `pnpm migrate` args passing: package.json uses `--env-file-if-exists=.env.local`. Keep that in the new script line.

### 4. dev:prod (`scripts/dev-prod.mjs`)
- **Structure.** Export `run(deps)` like dev-token.mjs so tests inject: token step, docker, tcp probe, file read of `.env.local`, password prompt, spawn. Use the same main-guard idiom as dev.mjs and dev-token.mjs.
- **Step 1, token.** Read the token file at `tokenFilePath(env)` (import from dev-token.mjs, which exports it). Parse the JWT payload and require `exp - now > 120`. Use a shape check (`JWT_SHAPE` is not exported; export it or duplicate). If stale, run `node scripts/dev-token.mjs` with `stdio: "inherit"` through the injected spawn (needs a TTY for raw mode); then re-read and re-validate. Stop with exit 1 if still not fresh.
- **Step 2, tunnel.** `docker inspect -f {{.State.Running}} <name>`; if not `true`, `docker start <name>`. Use `spawnSync` with an args array, `shell:false`, and validate the container name against `/^[a-zA-Z0-9][a-zA-Z0-9_.-]*$/` (SIMAP_PG_TUNNEL is user-controlled). Windows: `docker` resolves to `docker.exe`, fine without a shell. Then a TCP connect to 127.0.0.1:<tunnel port> with a timeout (about 2 s, retry for ~10 s after a fresh start). Use the same port the classifier uses (`SIMAP_PROD_TUNNEL_PORT`), not a literal 15432. A TCP answer only proves the port is open, not that the DB is up; fine for readiness, the password step will show auth errors.
- **Step 3, `.env.local` line check.** Read the file as text, line by line, and test `/^\s*(export\s+)?DATABASE_URL\s*=/` (also ignore lines starting with `#`). Do not echo lines. Missing file is fine. Refuse with exit 1 or 2 and a message that names the file and variable, not the value. Cover quoted-key and BOM edge cases: strip a leading BOM. Also refuse when the shell already has `DATABASE_URL` set? The ticket does not say it, but a pre-set DATABASE_URL in the process env is overridden by the child env anyway; still, ignore it rather than refuse. Also drop other db variables from the child env: delete PGHOST, PGPORT, PGHOSTADDR, PGPASSWORD, PGUSER, PGDATABASE, PGSSLMODE, PGSERVICE, so the URL is the only source. Also remove `NODE_OPTIONS` inspect (dev.mjs `assertNodeOptionsSafe` already throws; it is not called by dev-prod unless it delegates to dev.mjs's main. Reuse via export).
- **Step 3, password prompt and encoding.**
  - Hidden input needs a TTY; refuse when `!process.stdin.isTTY`, as dev-token does. `promptPassword` in dev-token.mjs is not exported, so either export it or move it to a shared `scripts/lib/prompt.mjs`. It uses raw mode, which means paste works but no multi-byte handling issues (iterating `for (const ch of chunk)` is code point safe).
  - Build the URL with the URL API rather than string concat: `const u = new URL("postgres://127.0.0.1:15432/simap"); u.username = "simap"; u.password = pw;`. The WHATWG setters percent-encode the userinfo set, but they do NOT encode every character `pg-connection-string` and libpq treat specially in all cases. Safer: `encodeURIComponent(pw)` then assign using string concat, and round-trip test with `pg-connection-string parse()` against passwords containing `@ : / ? # % & + space ' " \ [ ]`, non-ASCII, and a lone `%`. Note: the URL setter would double-encode an already percent-encoded string (`%` becomes `%25`), so do not call encodeURIComponent and then the setter. Choose one method and test it.
  - Empty password: refuse (exit 1) rather than start with a passwordless URL.
  - Host is 127.0.0.1, port is the tunnel port, db `simap`, user `simap` (constants, optionally env overrides validated). Do not append sslmode unless tudocuatui does (tunnel is already TLS-terminated by cloudflared; adding `sslmode=disable` is probably wrong, leaving no sslmode keeps the pg default of no SSL). Check tudocuatui's `scripts/start-dev.sh` for what it passes.
  - The password stays in a local variable and the child's env only. It is never put in argv (visible in process listings), never printed, never in an error message. Wipe the variable after spawn (`pw = ""`, cosmetic). Wrap the unexpected-error path to print a fixed message (pattern used in dev-token).
- **Step 4, child.** Set `SIMAP_DB_TARGET=production` in the child env as well, so any dev script the child's shell inherits refuses. The child is the Next dev server, which does not run those scripts, but it costs nothing and documents the state. Also set `NEXT_PUBLIC_SIMAP_DEV_TOKEN=1` through `devEnv()` and argv from `nextDevArgs([])` (exported from dev.mjs). The simplest, consistent approach is importing `nextDevArgs`, `assertNodeOptionsSafe`, `devEnv` from dev.mjs. dev.mjs's own main-guard does not fire on import, good.
- **Dev token to the browser.** Not in scope here, SIM-028 handles it (token via env or file); confirm SIM-028's server-side path reads the token file and nothing else is needed from dev-prod.
- **Ctrl-C.** Raw mode is turned off before the spawn; `stdio: "inherit"` lets the child receive the SIGINT from the terminal. In the parent, on SIGINT do nothing except wait for the child, then exit with its code. On Windows, call `child.kill()` in a `SIGINT` handler as a fallback, and make sure `stdin.setRawMode(false)` is restored in `done()` on every path including errors, otherwise the terminal is left without echo.
- **Banner.** Print after the checks and before the spawn: "production data: every change is real". Stderr or stdout, either way, no URL.
- **Readiness (`/api/readyz` 200).** This is a manual/test criterion; the unit tests inject the spawn.
- **Exit codes.** Suggest 1 for a failed step and 2 for a configuration refusal (`.env.local` has DATABASE_URL), matching the rest of the repo.
- **Tests.** Injected deps tracing the call order: [token check, (token run), docker, probe, env-file check, prompt, spawn]. Cases: token fresh skips dev-token; token stale runs it; dev-token fails, so no docker call and no prompt; docker start fails, so no prompt; probe fails, so no prompt; `.env.local` has DATABASE_URL, so no prompt (and where this check sits relative to the token and tunnel steps: ticket lists it as step 3 before the prompt; moving it to the very first step is cheaper for the user and does not break the ticket's order criterion, but the criterion says "stops before asking for the password when the token or tunnel step fails", so any order that keeps the prompt last is fine; recommend doing the `.env.local` check first because it needs no network and no prompt); the spawn env contains DATABASE_URL with an encoded password, `SIMAP_DB_TARGET=production`, and does not contain PG* vars; the captured stdout/stderr never contain the password or the URL; no file writes (inject fs and assert none).

## Risks
- **Container regression** if migrate.js imports a classifier that is not COPY'd into the image, or one that imports `pg-connection-string` (devDependency only). High-path files; the ticket is gated "none" but Dockerfile and db/migrate.js are probably High in `.github/risk-tiers.yml` (check it); the plan may need approval.
- **NODE_ENV=production is not a safe container discriminator**: a laptop user can set it. If the guard allows prod whenever NODE_ENV=production, `NODE_ENV=production pnpm migrate` bypasses it.
- **Port-only classification is incomplete.** Another forwarding port or a remote prod host (non-local, already refused for the four scripts but not for migrate and migrate-smoke today) will not be detected as production by migrate.js. For migrate (non-container) the stricter rule is "local hosts only": refuse any non-local host as well, not only prod-by-port. Recommend the pnpm-side wrapper use the full `assertDevSeedTarget` (local only, not production, not 15432), the same as the other four.
- **`.env.local` is read by `--env-file-if-exists`** before the script starts. A prod URL there is still caught by the guard, because the guard reads process.env after the file is loaded.
- **`SIMAP_PROD_TUNNEL_PORT` set to a wrong value** disables the 15432 protection. Mitigation: always also refuse 15432? If the override replaces the default, a user who sets it to 16000 loses protection on 15432. Recommend the check refuse BOTH 15432 and the override.
- **Password encoding mistakes** produce a silent auth failure or, worse, a URL that parses with a different password or host (`@` or `/` in the password). The round-trip test with the same parser pg uses prevents this.
- **Windows specifics.** `docker` via spawn needs no shell; `.cmd` shims (pnpm) do. Calling `process.execPath` with the script path avoids that, as dev.mjs does. Raw mode only works on a TTY; Git Bash/mintty may not provide one (dev-token has the same limit).
- **Token file read.** dev-prod reads the token to check expiry; do not print it, and do not pass it on the command line.
- **Tests that spawn scripts** can accidentally connect to a real local DB or tunnel if the guard is broken. Use a closed port and assert exit code 2, with a timeout.
