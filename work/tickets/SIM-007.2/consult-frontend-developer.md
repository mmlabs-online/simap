## Findings
1. **`/auth/orgs` shape is still undocumented.** consumers.md "Organizations" (lines 132-137) says only "`GET /api/v1/auth/orgs?account_id=` (the caller's orgs for the calling app, with their roles)". It gives no JSON body, field names or envelope. Q18's tolerant parser is still needed. Facts that ARE confirmed:
   - GET is cookie class (`credentials: "include"`, `X-MM-App`), with `account_id` as a query parameter.
   - Each org has a UUID, a name, probably a slug, and roles.
   - Line 374-379: a token requested WITHOUT `org_id` carries app-scope roles only, "enough to create or pick an org". `org` appears in the token only when `org_id` was sent.
   - So the picker can call `/auth/orgs` with the org-less token or the cookie. Mint an org-less token first only if the endpoint needs a bearer; the doc says cookie.
2. **`org_access_denied` is confirmed:** 403 on `/auth/token`. One answer for "no role of this app in that org", "org unknown" and "org suspended" (line 128). The doc's instruction is "Re-list the user's orgs". Related: 422 `org_not_supported` (an app with `org_mode = none`) is a bug code, not a user case. 422 `validation_error` is a bug. Map them to the generic retry or error view, not the picker.
3. **Denied-org loop reality check.** Because the three causes share one answer, a suspended org may or may not still appear in `/auth/orgs`. The plan's `exclude` parameter on `decideOrg` is right and must be kept. It must live in the gate for the current entry attempt (a local variable, not persistent), plus the remembered key cleared.
4. **Current code state:**
   - `tokenStore.renew()` calls `client.token(accountId)`. `NOTIFY_CODES` is `["session_invalid","not_member","email_unverified"]`.
   - `onMessage` filters only by `accountId`.
   - The AuthGate `View` union has `noOrg` but no picker.
   - `authChannel.parseAuthMessage` constructs a fresh object with known fields only. An old tab running the previous build will drop `orgId` and still post org-less messages. See Risk 1.

## Recommendations
1. **`decideOrg` purity** (AC "picker decision", testable without React). Signature:
   `decideOrg({orgs, remembered, exclude}) → {kind:"enter", org} | {kind:"pick", orgs, notice?} | {kind:"none"}`.
   - Use an options object (three positional nullable args are easy to swap).
   - Filter `exclude` out of `orgs` first, then decide: 0 left → `none`, 1 left → `enter`, several → `enter` the remembered org if it is in the filtered list, else `pick`.
   - **Decision to flag:** after a denial, "exactly one org left" enters it automatically. That is fine (the user did not choose the denied one), but show the "no longer have access" notice on the next screen. So `enter` should carry `notice?: "org_denied"` and the gate must hold the notice through the `checking` → `ready` transition, or the notice is lost. Simpler and safer: after a denial, never auto-enter; always `pick` (or `none`) with the notice, except when exactly one org remains and `exclude` was empty. Recommend this simpler rule: if `exclude` is non-empty, never `enter`. It is also loop-proof by construction. Plan said the opposite for the one-left case, so put this to Ming/plan as a deliberate change.
   - Compare ids case-insensitively (the existing code lowercases UUIDs); normalize in `identityClient.orgs()` to lowercase.
   - Pure inputs only: no storage, no client, no clock. Tests: table of 0/1/2+, remembered listed/unlisted/null, exclude present/absent/only-org, duplicate ids, case differences, input not mutated.
2. **Loop prevention as a state machine**, not just a pure function. Give the gate a per-attempt budget: `{denied: Set<orgId>}` that lives in a ref, reset on sign-in, on an explicit user pick, and on `seq` change. An org enters at most once per attempt; a second `org_access_denied` for an org already in `denied` goes to the picker with the notice and without auto-enter. An explicit user click on the picker always tries (no exclusion for a deliberate pick, but the denied org may be shown as disabled with a hint if the list still returns it, optional). Test as a tiny pure reducer, e.g. `nextOrgStep(state, event)` in `src/lib/identity/orgs.ts` (events `orgsListed`, `denied`, `picked`). That also answers the earlier open question 6 for this slice: the org flow is the part worth keeping pure.
3. **Token store design (per-tab org).**
   - Add `orgId` closure state, `orgId()` and `selectOrg(id)` to the `TokenStore` interface. Add an `OrgIdStorage` (read/write/clear keyed by account) as an injectable option, like `storage`, so tests can fake it.
   - `selectOrg(id)`: `reset()`, set `orgId`, persist (account-scoped), `renew()`. If renew fails with `org_access_denied`, the `.catch` branch must clear `orgId` AND the persisted value, keep `id`/account, and set `token = null`. Throw so the caller (gate) can handle; also add the code to `NOTIFY_CODES` for background renewals.
   - `renew()` captures `orgId` into a const along with `accountId` and `epoch` at start. After the await it compares `epoch`, which already covers selectOrg (reset bumps it). Pass `client.token(accountId, orgIdAtStart)`.
   - Org-less state is legal: after sign-in the store holds an account but no org. `renew()` then mints an org-less token. Decide explicitly: the `/api/me` call would answer `org_required`, which is the existing trigger for `needOrg`. Keep that (it reuses SIM-006.2's path and costs one extra round trip); do not add a separate "is org set" shortcut in the gate. Optional optimization: if `store.orgId()` is already set from remembered storage on `restore()`, mint with the org directly, so the normal path for a returning user is one token call plus `/api/me`.
   - `signOut`, `forget`, `session_invalid`, remote sign-out: clear the remembered org alongside the account id, using the same "clear only while it still names `gone`" guard as `forgetStored` (BUG-007 pattern). A remembered org stored under key `mm_org_id:<accountId>` makes the guard natural: clear the key for `gone` only.
   - `continueAs` / `signIn` (`adopt`): set `orgId` from the remembered value for the NEW account (not the previous one) or null. Easy to miss: `adopt` must reset the in-memory `orgId` before `renew`, else account B mints with account A's org.
4. **authChannel change** (protocol, flag in the plan):
   - Add `orgId: string | null` to the `token` message, validated in `parseAuthMessage` (UUID or null; reject any other type).
   - Do not bump `v`; keep `v: 1` but treat a missing `orgId` field as "unknown". Rule in `onMessage`: adopt a token only if `msg.orgId` (lowercased) equals this tab's `orgId` (lowercased), and an absent `orgId` equals null. So an old-build tab's org-less message is ignored by a tab with an org (safe, merely a missed share) and adopted by a tab with no org. That is correct and needs no version bump. Test both directions plus case differences.
   - `signedOut` stays by account only (sign-out is account-wide).
   - Cross-tab nuance: tabs on the same account but different orgs both renew their own tokens; the Web Lock serializes them but does not share results, so with two orgs in two tabs each renewal now also costs a lock wait and neither can reuse the other's token. Acceptable. The `fresh() && token !== rejected` shortcut inside the lock stays correct because `token` is per-tab.
   - `remembered org` (localStorage) is shared by all tabs of the account: last switch wins for NEW tabs; open tabs keep their own. State this in copy/docs so nobody expects follow.
5. **Remembered org per account.**
   - `src/ui/auth/orgId.ts` modeled on `accountId.ts`: `readOrgId(accountId)`, `writeOrgId`, `clearOrgId`, UUID-validated, lowercase, try/catch. Key `mm_org_id:<lowercase accountId>`.
   - Write it only after a successful mint with that org (not on click), so a denied pick is never remembered. Clear it on `org_access_denied` for that org (only if the stored value equals the denied id, to avoid clearing a newer choice made in another tab).
   - Tests with a fake storage: per-account isolation, invalid UUID ignored, clear-if-equal.
6. **Picker/switcher components** (`src/ui/org/OrgPickerView.tsx`, props only):
   - Props: `{orgs: {id,name}[], currentId?: string, notice?: "denied" | "load_failed", busyId?: string|null, onPick(id), onCancel?}`. `onCancel` present means switcher mode (a dialog or panel with a Cancel); absent means entry mode inside `AuthLayout` (no cancel, but a "Sign out" link is useful, because a user who cannot pick has no other exit; reuse the existing sign-out action).
   - Markup: a `<ul>` of `<button type="button">` items, the org name as the accessible name, `aria-current="true"` for the current org (also a visible check icon, not colour only), `disabled` plus `aria-busy` while one is being entered (prevent double mint). Notice in an `aria-live="polite"` region (reuse `Notice`). First item autofocus in entry mode only (not in a dialog that already manages focus; use the existing `EntityFormDialog` pattern if the switcher is a dialog, so focus trap and Escape come for free).
   - Long names: truncate with `title`? Use wrapping, not truncation; names are user data and must render as text (React escapes; never `dangerouslySetInnerHTML`).
   - The switcher dialog fetches the list on open with a loading/failed state (`Notice` + Retry), shows the current org marked, and picking the current org just closes. Cancel/close leaves everything untouched (no generation bump).
   - `Session`: add `orgName` and `canSwitchOrg`. Hide the swap button when `canSwitchOrg` is false instead of showing a disabled one (a permanently disabled control with no explanation is a minor a11y smell), or keep it disabled with a tooltip; pick one and cover it in `AppShellView.test.tsx`. Session org name from the `orgs()` list (matched by token's org id) is acceptable here because `/api/me` returns the org name only after S1; prefer `/api/me`'s `org.name` when present.
   - Copy in `src/ui/copy/org.ts` (D36), and add it to whatever `copy.test.ts` / `no-literals.test.ts` enumerate (check `no-literals.test.ts`: it likely forbids string literals in new `src/ui/**` files, so views must take all text from copy). Error mapping for the notice goes via a `code` → copy map, like `copy/api.ts`.
7. **Gate wiring (hotspot after SIM-006.3).** New View kinds: `orgPicker {orgs, notice?}`; `noOrg` stays. `needOrg` is a flow decision, not a View. The gate runs `orgs()` in the `apply` step; the `orgs()` call must be guarded by the `alive()`/`seq` check like the existing `noOrg` branch (`AuthGate.tsx:147-154`). Failure of `orgs()` (network) goes to the existing `retry` view, not to `noOrg` (do not tell a user with orgs they have none because of a timeout). Sign-out must stay reachable on `orgPicker`, `noOrg` and `retry`.
8. **Tests without jsdom:** `orgs.test.ts` (decideOrg + reducer), `tokenStore.test.ts` additions (fake org storage, fake channel: cross-org message ignored, selectOrg drops in-flight older answer, denied clears persisted org and keeps account, adopt for account B does not use A's org), `authChannel.test.ts` (`orgId` parse: missing/null/UUID/invalid), `identityClient.test.ts` (`orgs()` tolerant parse: envelope variants `[...]` and `{orgs:[...]}` / `{items:[...]}`, id field `id` or `org_id`, names trimmed, non-UUID ids dropped, duplicates removed; `token()` body includes `org_id` only when given; 403 `org_access_denied` mapping), `views.test.tsx`-style `renderToStaticMarkup` for `OrgPickerView` (entry vs switcher mode, current marker, busy, notice, button names), `flow.test.ts` additions.

## Risks
1. **Old build tabs during deploy**: a tab on the previous build posts org-less messages with no `orgId`; handled by the "absent = null" rule in Rec 4, but only if `parseAuthMessage` does not reject unknown shapes. Test it.
2. **Cross-account org leak** in `adopt` (Rec 3) and in the remembered-org read (key must be account-scoped).
3. **Wire shape guesses**: `/auth/orgs` field names are unknown. Keep all guessing inside `identityClient.orgs()`; if no recognizable list comes back, throw a clear parse error (to `retry`), not an empty list (which would show "no organization" to a real member). Ming check after merge is mandatory (M-1, two orgs on one account).
4. **Notice lost / loop** if the denied-org handling is done only in `viewForTokenError` (stateless). The per-attempt `denied` set (Rec 2) is the safeguard; without it, "suspended org still listed + remembered" can loop (enter → denied → list → enter).
5. **Switcher stale list**: user switches to an org they were removed from in the meantime: the mint returns `org_access_denied`; the gate must return to the picker with a fresh list and keep the previous org's data unmounted (they were already unmounted by the `flushSync` checking step). Decide whether a failed switch should restore the previous org (it was reset). Recommend: no automatic restore; the picker is shown, with the previous org still selectable.
6. **Mid-session background denial** (token timer renewal gets `org_access_denied`): `store.subscribe` must route it to the picker, which will unmount a screen the user was using. Expected, but it deserves a notice and a test.
7. A user-pick of an org by id relies on server-side check only (R6); the client list is a convenience. Do not skip the server's `org` claim check on the client's say-so.

## Open questions
1. After a denial with exactly one org left: auto-enter with notice (plan) or always show the picker/none with the notice (recommended, simpler, loop-proof)? Default: always picker/none when `exclude` is non-empty.
2. Switcher: dialog or inline panel? Default: dialog reusing `EntityFormDialog` conventions.
3. Hidden or disabled switcher for single-org users? Default: hidden (`canSwitchOrg` false). Note this requires the org list to be known at entry (an extra `orgs()` call on every sign-in even for remembered orgs); alternatively fetch lazily on first open and keep the button visible. Default: fetch at entry only when the gate already listed orgs (picker/none path); for a remembered org, show the button and let the dialog fetch lazily; if the list has one entry, show "You only belong to this organization". This avoids an extra round trip on the hot path. If Ming wants it hidden for single-org users, the extra call is required.
4. Should the `/auth/orgs` response also be supplied by Ming now (paste a real example) to replace the tolerant parser? Q18 default stands.
5. Does `/auth/orgs` need the cookie only, or also a bearer? consumers.md says cookie class; assume cookie, no token needed.
6. Is changing the plan's S2 auto-enter-after-denial rule (Rec 1) acceptable?
