## Findings (merged slice 1 code, what images now need)

- **API layer** (`src/ui/deviceTypes/device-types-api.ts`): `call()` always runs `res.json()` on success through `read`. The image calls need their own readers. PUT returns a `DeviceTypeDto` (with the new `imageVersion`), so `json` can be reused. DELETE returns 204 with no body, so use the `remove`-style reader. GET returns bytes, so a new reader should do `res.blob()`. `ApiFetch` takes `RequestInit`, and `apiFetch` is `fetch` with a bearer, `cache:"no-store"` and `redirect:"error"`. So no `If-None-Match` ETag round-trip is available through the browser cache. The in-memory cache per `{id, imageVersion}` is the only caching.
- **Body type**: `apiFetch` re-sends once on 401/403 and throws if the body is a `ReadableStream`. Send a `Blob` or `Uint8Array`, not a stream. `File` or `Blob` are fine and re-sendable. Set `headers: {"content-type":"image/png"}`. Do NOT add a JSON content-type (`withBody` is JSON-only).
- **Errors**: `apiErrorMessage` (`src/ui/copy/api.ts:54-59`) already has copy for `image_not_png`, `image_bad_size`, `image_too_large`, `image_changed`, `images_unavailable` and `drive_error`. Slice 3 needs no new refusal copy. `settleSave` maps result to message and treats `not_found` as done. Reuse it for image results. A deleted type during the image step also gives `not_found`, so "done" is correct.
- **Dialog** (`DeviceTypeFormDialog.tsx`): `submit` is create or patch, then `onDone()`. The `key={item?.id ?? "new"}` remount means that once a created type is saved, the dialog cannot become "edit mode for the saved type" by itself. `item` is a prop and `DeviceTypePage` owns it. See the save sequence below.
- **Form fields** (`DeviceTypeFormFields`) is a pure, props-only component rendered with `renderToStaticMarkup`. Keep the image section the same way: a pure `DeviceTypeImageField` taking props (`previewUrl`, `onPick`, `onRemove`, `error`, `busy`). Hooks and effects stay in the Inner component or a hook.
- **List**: `DeviceTypesView` is pure and has no image slot. `renderRow` is the place for a thumb. A hook is needed outside the View (in `DeviceTypesLoaded`), passed as a prop such as `imageUrl: (t) => string | null`. That keeps the View testable via static markup.
- **Test env** is Vitest `environment: "node"`, with no DOM, no `URL.createObjectURL` guaranteed (Node has `URL.createObjectURL` for Blobs, but the browser `Image` and `File` input are absent) and no `renderHook`. Existing tests use `renderToStaticMarkup`. "Component tests" in the ticket must therefore mean pure-function tests plus static markup.

## Recommendations

1. **Pure image check** in `src/ui/deviceTypes/device-type-image.ts` (no effects, easy to test in node): `checkImageFile(size: number, read: () => Promise<Uint8Array>): Promise<{ok:true; bytes} | {ok:false; code}>`. Order: `size > IMAGE_LIMITS.maxBytes` gives `image_too_large` before reading, then `validatePng(bytes)` gives `image_not_png` or `image_bad_size`. Map the code through `apiErrorMessage` so the client messages equal the server ones. Tests (AC3): fabricated PNG bytes built with a small helper (signature + IHDR + IDAT + IEND with CRC; copy or reuse the helper from the existing `src/lib/validate/png.test.ts` if it exports one, otherwise write a tiny one); valid 24x24 ok; 16x16 gives `image_bad_size`; 20481 bytes gives `image_too_large` and `read` is not called; text or JPEG bytes give `image_not_png`; empty file. Note `accept="image/png"` is advisory only, so the check must not rely on `file.type`.
2. **Blob URL cache** as a plain class or factory, `createImageUrlCache({ load: (id) => Promise<Blob|null>, create = URL.createObjectURL, revoke = URL.revokeObjectURL, limit = 4 })`. Inject `create`/`revoke` so node tests use fakes and need no jsdom. Key `${id}:${imageVersion}`. Behaviour:
   - `get(type)` returns a URL promise, or null when `!hasImage`.
   - Dedupe in-flight requests.
   - A concurrency limit of 3-4 (as the plan says).
   - On a newer `imageVersion` for the same id, revoke the old URL. On `dispose()` revoke all.
   - Race rule: if disposed or superseded while a load is in flight, revoke the freshly created URL immediately and do not store it.
   - A failed load is cached as `null` for the session or retried on version change, and shows the placeholder (no inline error per row).
   - Tests: hit/miss, same key loads once, version bump revokes the old one, dispose revokes all, a late result after dispose is revoked, concurrency cap never exceeded.
3. **React hook** `useDeviceTypeImages(api, types)`: a `useRef` cache, a `useEffect` cleanup that calls `dispose()` on unmount, and state bumped on load. Prune entries for ids no longer in the list after reload. Under React strict mode the effect runs, cleans up and runs again, so create the cache lazily inside the effect (or recreate after dispose) so the dev double-mount does not leave a disposed cache. This hook is thin and is not unit tested in node, so keep logic out of it.
4. **API additions** in `createDeviceTypesApi`: `getImage(id): Result<Blob>` (blob reader, `fail("internal")` if not an image), `putImage(id, bytes: Uint8Array)` returning `DeviceTypeDto`, and `removeImage(id): Result<null>`. Add to `device-types-api.test.ts` with a fake fetcher: check the method, the `content-type: image/png` header, the body is not a stream, and 422 `image_too_large` gives `{ok:false, code}`. For the `Uint8Array` body, check that TS accepts it as `BodyInit` (the route file needed `as BodyInit`, so a `new Blob([bytes], {type:"image/png"})` body may be cleaner).
5. **Dialog preview**: use a staged `URL.createObjectURL(blob)` created when a file passes the check. Revoke it on replace, on Remove, on unmount and after a successful save. Keep the staged state `{ bytes, url } | {remove: true} | null`. Reset the `<input type=file>` value after a rejected pick so choosing the same file again re-fires `onChange`. Show the existing image in the dialog for edit mode through the same cache (`item.hasImage` and not staged). Use `<img alt="" ...>` (decorative next to the label) with `style imageRendering: "pixelated"`, a fixed size such as `w-12 h-12`, and Tailwind `[image-rendering:pixelated]`. Remove is a button, shown only when there is an image (existing or staged) and disabled while submitting. A staged Remove only takes effect on Save, to match the save sequence (state it in the copy).
6. **Save sequence** (as the ticket says), implemented as a pure function `runSave(steps)` or `saveWithImage({ saveType, imageOp })` returning `{kind:"done"} | {kind:"typeSavedImageFailed", saved: DeviceTypeDto, message}| {kind:"error", message}`. This is testable in node with stub steps. Rules:
   - Create returns the DTO, whose `id` is needed for the PUT. So the dialog must adopt the saved type: hold `saved` in Inner state and use `saved ?? item` for subsequent submits (`toPatchBody(form, saved)`). Keep the dialog's `key` stable, since changing `props.item` would remount and lose the staged image and error. Do not remount on the create-then-fail path.
   - If the type step is `unchanged` and an image op is pending, skip PATCH and run only the image step. Currently `unchanged` calls `onClose()`, so this branch needs changing: unchanged plus image op is not close.
   - If the type step saved but the image step failed: stay open, show the message inline (`apiErrorMessage(code)`), keep the staged image so Save retries only the image step (do not re-POST, which would create a duplicate and hit the unique name). Make sure the next submit after a create skips `api.create`.
   - On `onDone`, the list must reload to pick up the new `imageVersion` (already done by `done()`). Because the cache is keyed by version, the new image loads, and the old URL is revoked.
   - After a failure the parent list is stale (the type exists but the list shows nothing new). Closing the dialog by Cancel after "saved type but image failed" should still reload the list: call `onDone` or a separate `onChanged`. Otherwise a created type is invisible until reload.
   - `image_changed` (409): the message says reload and try again. Map to staying open. The retry will conflict again until the list reloads, so also trigger a list reload in the background (or accept the Close-then-reload above).
7. **Slot fieldset should-fix** (SIM-036.3 review Issue 1): make `<legend className={CAPTION}>` the first child of `<fieldset>`, and wrap the radio column plus `<DeskSlotDiagram>` in an inner `<div className="flex items-start justify-between gap-3">`. The radio column stays `flex flex-col gap-2`. Add the markup test `/<fieldset[^>]*><legend/`. Put the image field after the fieldset as its own `<fieldset>` or labelled group with the legend first, and give the file input a real `<label>` (the input is visually the native control; do not hide it without an accessible replacement). Show the inline image error with `role="alert"` near the field, or use the dialog's existing `error` slot.
8. **Out of scope hygiene** (R1/R4): all new code under `src/ui/deviceTypes/**` imports only `@/lib/validate/png`, `@/lib/api`, and `@/lib/device-types`. Copy goes in `src/ui/copy/deviceTypes.ts` (labels: "Image", "Choose PNG", "Remove image", "Placeholder", hint "PNG, 24 x 24 px, up to 20 KB"). Do not touch routes.

## Risks

- Blob URL leaks: strict-mode double effects, an unmount while a load is in flight, and a dialog closing with a staged URL are the three classic ones. The cache's late-result rule and unmount cleanups cover them.
- Create succeeds but PUT fails, then user presses Save again: a duplicate POST gives a 409 name conflict unless the dialog adopts the saved type (Recommendation 6). This is the most likely bug.
- The list-row image fetch is N requests on page load, each with the bearer. The concurrency cap matters and `apiFetch` may re-mint tokens under 401. Per-row failures must not show an alert for every row.
- `validatePng` is structural only (no pixel decode). A structurally valid but undecodable PNG would still show a broken `<img>`; add `onError` fallback to the placeholder.
- 20 KB `File.arrayBuffer()` is cheap. Reading before the size check is the only risk, so keep the order.
- Node tests cannot cover the real `<img>`/`File` interplay. Add a manual check (the ticket's manual line) with a 24 px PNG, a 32 px PNG, a JPEG renamed `.png` and a >20 KB PNG.
